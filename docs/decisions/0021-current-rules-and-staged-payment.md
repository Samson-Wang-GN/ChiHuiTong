# ADR-0021 核销时合同与渠道、零元结算及支付分阶段交付

- 日期：2026-09-12；状态：业务规则已确认，目标设计已记录，代码尚待实施。
- 关联：REQ-042、TASK-077～080；覆盖旧ADR中冲突的未决口径，不改写历史测试事实。

## 决定

1. 将预约历史、核销业绩归属及当前跟进权限分开。核销读取届时已生效的门诊渠道变更；保存渠道和合同/条款/费用快照后，账单按该不可变事实归集。预约时渠道仅追溯，不决定变更后核销的收款方。权益来源资源方不变，既有核销不随后续变更重新分配。
2. 存量核销优先适用新合同，没有新合同则取最近一版。只选择该主体经审核且已生效过的适用条款，待审/未来合同不抢占；完全缺失不猜测。存量回溯与当前新业务授权分离，以免过期合同恢复新业务权限。
3. 0元合作方结算单是真实入单事实，但不是收付款事实。采用“无需付款”状态，保留明细及入单唯一约束，不生成0元付款或人工确认；不会因为跳过付款流程而重复归集。
4. 客户可选资料只补空，来源订单原始值独立保存；并发审核原子复核空值，0岁不当空值。不得覆盖客户本人资料或跨机构原始值，不改变手机号/姓名匹配和平台编号规则。
5. 微信支付本期开发，外部商户资料缺失不阻塞代码和隔离模拟测试。真实适配与测试网关分离；生产默认关闭未配置支付，禁止自动切成模拟成功。单元/契约/幂等/异常测试不能替代真实微信和真机支付。收款主体、商户模式及开通能力就绪后补真实联调，不能擅自授权第三方资金操作。

## 取舍与边界

不按预约时预锁费用或旧渠道业绩，不把0元伪装已付款；保持现有合同授权、权限、线下凭证及原始审计。试点无业务配额不等于无限单次资源消耗；使用异步、分块、限流和容量验证，而非硬编码业务总数上限。

本ADR不决定正式后端框架，不声称接口或数据库已经存在。支付代码首先依赖正式身份、账单版本、事务和持久化边界，详细方案由Codex制定；同商户重试、回调验签、金额版本、线下线上互斥及机构隔离必须在服务端验证。当前原型的模拟支付成功不作为真实资金证明。

## 验证与文档一致性

任务分为规则与文档、原型同步、支付代码/可执行测试、真实联调四项，分别记录状态与证据。现有测试及截图保留其原版本，不用更新需求号伪造新验收。旧ADR明确标注被替代的条款；README、需求、架构和设计/评审文档统一显示需求0.32与运行原型差距。全部运行测试仍只能在指定公共开发测试服务器执行。
