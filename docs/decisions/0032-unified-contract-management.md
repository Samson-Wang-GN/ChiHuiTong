# ADR-0032 统一合同管理与内嵌签约主体

状态：已确认，2026-09-16；REQ-049 / TASK-108。

REQ-050补充：单店新增向导内嵌合同和主体信息，联合申请自动进入统一合同台账。ClinicAgreement.onboarding_change关联本次资料申请，联合审核事务原子发布资料、合同、产品及上线；独立审核入口拒绝绕过，退回补正创建新版本并保留原申请。连锁仍分步处理。既有门店ID和主体不因补正重建。

支付码复用后端Pillow，增加固定qrcode 8.2仅将服务端验证后的微信code_url编码为PNG，不调用第三方二维码服务、不写文件、不缓存付款码；可移除适配器退出，不改变资金事实。[官方包说明](https://pypi.org/project/qrcode/8.2/)。模拟支付不生成可用真实付款码，真实商户验收仍独立待办。

合同跨客户资源方、渠道和门诊签约主体，放在机构/门店抽屉维护导致入口割裂。本轮将合同维护统一到独立合同管理，分类筛选和状态Tab；原模块只读展示及跳转。四角色独立入口、原服务端权限不合并。

签约主体仍有稳定数据库ID以承担付款和历史债务，但不设单独管理菜单。新合同选择已有主体或内嵌填写新主体，事务内建档、首个管理员及合同，失败一起回滚；代码防重复，续签复用。无覆盖门店允许草稿，最终审批前必须补齐；新增门店不自动伪造主体或合同。

为降低历史迁移风险，旧机构合同及三方合同继续使用既有模型，双方门诊合同使用ClinicAgreement；统一列表按类型查询已有模型。保留既有ID/版本/审计/结算快照。统一入口不意味着放宽跨渠道附件或总部患者资料权限。

合同草稿关联门店只允许尚无主体或本主体的本人范围门店；转移有旧合同/债务的门店仍由平台后续明确生效安排，不能在表单中隐式承接。测试、模拟验收和真实微信收款分别记录，不因代码提交宣称已验收。
