## 结论

小文件主要慢在后台任务排队，并非Excel解析本身。当前验收worker每次执行一轮后退出，systemd设置`OnUnitActiveSec=60`，实际`AccuracyUSec=1min`。上传的`excel.inspect`和下一步的`excel.validate`各自入队，但没有即时唤醒机制。

18:00以后观察到的21个任务启动间隔为60.003～93.746秒，中位数60.860秒。不是“每个文件固定耗时60秒”，而是取决于入队时刻和下一次唤醒。14.8毫秒的校验同样可能等近一分钟才开始。

只读核对最新2行导入：18:15:44.759创建识别任务，18:16:01所在轮次执行；18:16:08.012创建校验任务，18:17:01所在轮次才开始，18:17:03.133批次已确认。校验启动前约53秒处于等待。日志只有秒级启动记录，不能据此伪造该用户文件的毫秒级处理耗时。Outbox的`updated_at`并未在成功更新状态时同步刷新，不能用它作为任务完成时间。

检查时服务器load为0.00/0.02/0.08，可用内存约6.4GB，磁盘使用56%，无交换使用；全部5条Excel任务已完成、无重试及积压。以上是当时快照，不代表持续负载监控。

## 其他发现

1. **逐行查询**：`validate_import`每行调用`match_preview`查询一次客户；万行产生10,000次客户查询、总计10,027条SQL。执行SQL时间约2.60秒，完整任务约8.52秒，其余包含解析、Python处理、加密及写入。因此批量查询有价值，但不能声称消除查询后全部8.5秒都会消失。
2. **重复轮询**：`imports.js`已有每1.5秒刷新状态，下一步的`prepare`又每1.5秒请求状态，校验期间存在两条轮询路径。单次接口耗时很小，不是本次几十秒延迟的主因，但会增加请求量。
3. **90秒等待上限**：下一步等待校验的前端上限是90秒，实际已观察到93.7秒worker启动间隔；在不利入队时刻，可能处理尚未开始就提示等待超时。当前用户这次任务成功，不能把这个风险说成已经发生的失败。
4. **现有测试盲区**：`verify_web_backends.py`、`web_import_flow.py`在操作后主动调用worker，验证了业务结果但绕过部署调度等待，不能证明实际页面响应速度。后续必须单独覆盖真实常驻/定时消费方式。

## 建议修复顺序（尚未实施）

1. 首先调整本项目任务消费者为常驻、短间隔取任务，保留现有数据库队列、领取锁、重试和幂等；定时账单/预约调度仍按自己的频率执行，避免高频重复调度。无需为了这一问题引入共享Redis或新队列技术栈。
2. 将校验中的客户匹配改为有界分批查询，保留手机号/姓名冲突判断及租户数据边界，不缓存或记录明文客户资料。
3. 合并前端轮询；界面区分等待处理和正在处理，等待超过前端窗口不误判为业务失败，允许安全恢复查询。
4. 在隔离环境验证连续两阶段的真实用户等待、空闲CPU、重启恢复、并发领取和故障重试，再部署；保留原worker/timer配置回退方案，不操作共享服务。

本次已完成原因定位和基线测试，**没有进行性能修复或改变验收环境**。后续修复另行记录需求验收阈值与前后对比，不以调大前端超时替代消除排队等待。
