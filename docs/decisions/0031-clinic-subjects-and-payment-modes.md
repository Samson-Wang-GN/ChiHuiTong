# ADR-0031 门诊签约主体、门店覆盖与两种收款模式

- 日期：2026-09-16。
- 状态：需求及架构方向已记录，详细设计、迁移、原型、代码和验证待实施；不是已发布能力。
- 关联：[REQ-048（需求0.33）](../requirements.md)、[TASK-101～107](../tasks.md)。
- 替代范围：ADR-0005的每店三方合同/独立后付账单、ADR-0014的员工无任何付款权限，以及ADR-0016/0023中不适用于现付的锁费时点/支付对象；其余安全、权限及历史事实保留。

## 背景与已确认边界

连锁通常由总部统一签约、一次入驻多店并按周/月后付；单店不支持后付，完成服务后由前台工作手机支付当次获客费。付款责任为门诊侧合同签约主体，不是前台个人；无需负责人代付或逐笔审批。新门诊合同为平台—门诊合作主体双方纸质合同，渠道协助签署及寄送，平台收到原件签署、上传完整合同并审核后上线，回寄签收不是上线前置。

用户后续明确：**现付错误核销退款暂不考虑**。本期无现付退款申请、审核、人工退款登记闭环、执行、权益恢复或收益追回能力；已结清不允许直接撤销。采购订单原有取消/线下退款不变。可信付款已发生而本地处理失败仍须保留证据、幂等恢复或平台核查，不把未知结果当失败或重新收费。

## 当前代码约束（本轮只读核对）

- `models/catalog.py`：`Clinic.organization`和`Contract.organization`均为一对一；门诊合同类型显示平台—渠道—门诊，合同版本包含渠道及结算周期。不能仅改类型显示名就宣称支持总部合同覆盖多店。
- `models/finance.py`：`ClinicBill`绑定一个门店，按门店/出账日唯一；`PaymentAttempt`必须绑定账单。不能为现付每次伪造周期账单，也不能将总部账单挂在任意一家店上借用权限。
- `models/fulfillment.py`：核销已记录资源方、渠道和分配金额；既有核销归因、已结清状态及不可改删的业务事实需要兼容。
- 现有代码及历史服务器测试验证的是此前业务基线；未验证本ADR的新模型、总部权限和现付核销事务。

## 决定

### 1. 分离签约责任和服务门店，保留稳定ID

沿用Django/PostgreSQL模块化单体及现有Organization、Clinic，不新建集团ERP或另起技术栈。复用机构主数据承载经核实的签约主体，新增明确的合作主体—门店关系、合同版本覆盖及付款安排；品牌名不能作为主体关联键。

既有Clinic仍表示一个持证地址及预约/核销边界。门店加入连锁不改变患者、权益、预约、核销或账号历史ID，不把下游数据批量改归总部账号。合作关系、人员负责关系和历史交易快照分离；未来业务员交接不需要搬移交易（REQ-038）。具体新增表名、外键及约束在TASK-102评审确定。

同店同一时刻最多一套有效覆盖/付款安排；新增门店需审核覆盖依据及资质，不因挂名总部自动可营业。总部与门店经营主体不同时记录授权依据和总部付款责任。一个合作主体当前采用一套结算安排作为最小设计，不支持按店混用后付/现付。

### 2. 双方合同与渠道授权解耦

平台—渠道合同继续控制渠道可用推广产品和分配；门诊双方合同控制覆盖门店、获客收费依据、期限、责任主体和付款模式。新渠道归属不自动改签双方主体。每店仍只有一个当前渠道及业务员，核销归属按新规则保留快照。

线上内容审核、原件收签、平台签署、合同生效和逐店上线独立记录；单方签署照片与双方最终版分开版本。内容审核2工作日，原件物流时间不冒充内容审核处理时间；签署和寄送进入现有待办与审计体系。不接电子签API、不制作电子印章。

### 3. 后付账单归主体，现付订单归当次核销

后付以合同签约主体及结算安排归集周/月账单，每行保留门店、原合同版本和核销快照；总部整单结清前不按门店部分冲销。旧单店账单仍追收原债务，不能再归入新总部账单。周期切换只接管同一付款主体未出账交易，不转移旧款。

现付新增独立的核销付款业务对象，关联门店、预约、预锁报价、签约及付款责任主体、实际员工和可信支付事实；不生成待收周期账单，不采用余额账户。复用支付签名/验签、查单、关单适配边界；支付尝试扩展为明确约束的两种业务目标，禁止同时指向后付账单和现付订单，具体迁移在详细设计确定。

三方收益仍以有效核销为基础：后付有整单足额结清依据，现付有本单可信足额收款且核销完成依据，才允许合作方月度扫描历史未入单分配。统一判断收款证据，但不强迫现付通过账单关联判断结清。零元无需付款保存依据而非伪造到账；不生成平台自收款收益单。

### 4. 支付与核销使用可恢复的分阶段处理

1. 服务端鉴权、确认完成服务、检查预约/权益/最终预约日有效期、解析合同与报价。
2. 创建唯一有效现付订单，预锁金额、数量、合同/覆盖、渠道/资源方和分配快照，原权益保持预约占用；预约阶段仍不锁费。
3. 通过工作手机同机微信支付（小程序JSAPI）；后台辅助扫码不改变同机主路径。实际微信付款人与合同债务主体分开记录。
4. 服务端持久化可信支付观察，校验商户、订单、金额和币种；客户端成功回调不能判定到账。
5. 本地事务幂等提交核销、权益扣减、预约完成、费用与收益快照、已结清依据；外部网络调用不持有数据库长事务。
6. 通知丢失主动查单，断网/重试恢复原订单；已付款但核销未完成继续恢复，不新建收费。无法安全恢复保留已付款异常，由平台核查，不承诺退款闭环。

沿用现有支付尝试15分钟作为可审查技术默认；本地过期不等于渠道关单。未决订单期间互斥重复下单、预约取消/改期/未到恢复/72小时自动完成，以及影响报价的合同、主体、模式或渠道变更；先核实完成或确认未支付并关单再继续。后付仍在核销事务锁费；现付核销沿用付款前报价，避免支付中调价。

资金及业务终态以持久记录和幂等约束为准，不依赖页面是否打开。被停用员工不能再操作，但已可信收款的服务器恢复不会因其退出丢失。已核销现付禁止撤销；未结清后付普通/特殊撤销继续遵守REQ-037。

### 5. 最小授权扩展

- 总部管理员：已授权签约主体的合同、门店管理和统一账单；不由此共享全部门店患者名单。
- 门店管理员：本店资料、员工、履约和权限内合同/交易，不自动获得总部整单付款权。
- 员工：本店预约履约及现付核销订单创建、支付、查询/恢复；不开放合同、后付整单、凭证审批、退款或合作方费率。
- 渠道管理员/业务员：原负责范围内资料、覆盖摘要、产品和催收，不能替门诊核销、付款或看其他渠道的门店及总部整单。
- 待入驻受限账号：仅自身资料、合同信息填写及审核进度，不进入经营流程。

服务端列表、详情、附件、导出、计数和任务均用相同范围。跨渠道覆盖合同原件只向平台、签约主体授权人员和明确获权人员开放；普通渠道使用本方覆盖投影，不能以管理一店取得整份合同。Web保持四角色独立入口和Arco，两个小程序数量不变。

## 备选与取舍

- 拒绝“每店独立签约出账后人工汇总”：不能表达总部责任且重复催收/付款风险高。
- 拒绝“将所有门店合并为一个Clinic”：会破坏持证地址、员工隔离、预约和历史归因。
- 拒绝“先核销、创建现付欠款稍后再付”：实质为后付，违背单店限制。
- 拒绝“前台先扣权益，再依赖退款恢复”：增加本期明确延期的退款闭环，且无法用单个数据库事务保证外部资金回滚。
- 接受付款前短时预锁报价及支付处理锁：复杂度高于普通后付核销，但为确定金额和避免重复扣款所必需；不开启泛化支付编排平台。
- 接受本期现付错误核销不能自助纠正的限制，页面支付前必须明确展示本次费用/预约/服务完成确认；异常情况保留证据，后续真实业务驱动再定义退款。

## 实施、验证与回退边界

依TASK-102～107分步实施：数据迁移与约束→合同/门店覆盖及授权→现付闭环→总部账单及两类收益归集→各角色页面及小程序→服务器专项回归及独立真实支付验收。每个功能切片要有测试，不以最后一轮集成测试替代单项验证。

迁移使用扩展—校验—切换，先备份，保留旧主体、合同类型、账单及证据；无签署依据的数据列为待核实，不自动批量转为总部合同或现付。回退不能删除新收款记录；出现未决真实资金时先停新下单、保全流水、核实恢复，不退回只能识别旧账单的程序强行处理新订单。

所有测试仍仅在140.143.125.233的齿慧通隔离环境；本地本轮只做文档和静态检查，不同步服务器、不改数据库或部署。真实商户配置及真实支付验收是现付营业前置，模拟成功不能据此放行。支付、权限及迁移上线前须非作者评审。

## 本轮不做

不修改代码、原型或环境；不接电子签；不新增现付错误核销退款（包括人工登记闭环）、信用额度、钱包、预充值、负责人代付、多层集团及跨渠道客户营销。现付退款是已确认延期，不列为待定技术方案。
