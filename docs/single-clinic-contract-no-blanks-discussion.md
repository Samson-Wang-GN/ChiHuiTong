# 单店合同：无手填业务项讨论稿

状态：讨论稿，未经法务审核，不可直接作为正式签约范本。用户提出合同业务信息全部系统生成；以下具体条款与字段仍待确认，不代表系统已经具备新增能力。

## 合同正文示例

下面仅使用目前已支持的占位符；系统生成时还会在正文前添加合同信息摘要。签名和盖章位置是履行签约的区域，不是业务员填写合同条款的空白。

```text
口腔门诊福利履约合作协议

合同编号：{{number}}
甲方：{{platform_name}}
统一社会信用代码：{{platform_credit_code}}
乙方：{{subject_name}}
统一社会信用代码：{{subject_credit_code}}
合作门店：{{stores}}
合作期限：{{starts_at}}至{{ends_at}}
付款方式：{{payment_mode}}
合作产品及单次获客服务费：{{products}}

第一条 合作内容
甲方运营齿慧通平台，为客户使用权益提供门诊查询、预约、权益核验和核销记录等服务。乙方在本合同约定的门店和有效资质范围内，按双方确认的合作产品及服务规则为客户提供服务。

第二条 预约与核销
客户提交预约后，乙方按照实际接诊能力确认预约。乙方应核验客户权益及预约，并在确认约定服务已完成后按平台流程办理核销；不得虚构服务、重复核销或超量核销。

第三条 费用和付款
乙方按本合同所列产品和单次获客服务费，就有效核销向甲方支付费用。单店采用核销现付，乙方授权员工按平台流程确认信息并支付；付款责任由乙方承担。可信收款确认后完成该次核销。支付结果不明确时，双方应先核实原订单，避免重复付款。

第四条 合作管理
乙方应保持相关执业资质和门店资料真实有效，按适用要求独立承担医疗服务责任。合作产品、费用或其他重要条款发生变化时，双方应按约定办理确认，并保留原合同及历史交易记录。

第五条 信息保护
双方应依法在各自职责和授权范围内处理履约所需信息，采取必要保护措施，不得将客户信息用于未经合法授权的其他用途。

第六条 暂停、终止和争议处理
合同到期或合作暂停、终止时，双方应核对并妥善处理存量预约、权益及未完成事项。双方因履约发生争议，应先协商；协商不成的，依法处理。

本协议自双方依法签署后成立，按本合同所列合作期限履行；门店承接新预约还须符合平台审核和上线条件。本协议一式两份，双方各执一份。

甲方：{{platform_name}}                       乙方：{{subject_name}}
甲方签字／盖章区                              乙方签字／盖章区
```

## 字段和权限边界

| 合同信息 | 建议来源 | 经办边界 |
| --- | --- | --- |
| 合同编号 | 系统生成 | 渠道不可自行更改 |
| 平台主体和信用代码 | 平台管理员维护的模板配置 | 渠道只读 |
| 门诊主体和信用代码 | 门诊签约资料，经平台审核 | 渠道按权限录入或选择；不得填写未经核实的主体 |
| 合作门店 | 有权限的门店资料 | 单店只覆盖所列门店 |
| 合作期限 | 合同草稿中的生效、到期时间 | 渠道可否自主设定及允许范围待确认 |
| 产品和单次获客费 | 平台配置及合同选择形成的生成快照 | 渠道从授权范围选择产品，不得自由改费 |
| 付款方式 | 单店业务规则 | 系统固定为核销现付 |
| 正文和其他固定条款 | 平台认可的模板 | 渠道不可编辑 |

## 当前限制和待确认事项

- `{{products}}`现在只输出产品内部名称和单次获客费，不含单次核销数量、具体服务内容及限制条件。是否要把这些明确写入合同，以及使用内部名称还是客户可见名称，需确认后扩展字段和输出规则。
- 产品多项时，应由系统自动生成完整清单，不留产品行供手填。清单放正文还是独立附件待确认；无论放在哪里，都必须随合同版本一起冻结。
- 签字／盖章保留人工线下操作。签署日期是否需要显示、来源和如何确认尚未确定，不应随意用生成日期冒充真实签署日期。
- 含税、开票、支付手续费、实际收款主体和退款异常规则目前未确定。本讨论稿没有替双方作决定；正式签约前需明确并由平台固定配置或形成经审阅的固定条款。
- 草稿保存可以不完整；生成可签署文件前应检查必填字段、门店和产品授权。已打印文件有手写添加或修改业务条款时，平台应通过人工审核处理，不能假定系统能够自动发现。
- 合同正文和 PDF 摘要均应使用同一份快照，任何影响合同内容的变更需要重新生成并重新签署；既有合同和附件保留。
- 当前是业务讨论，不改变现有代码或正式模板；实际文本需法务结合收款、税务及个人信息处理方式审阅。
