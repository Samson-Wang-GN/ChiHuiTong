# ADR-0015 业务员交接采用负责关系变更（历史提议，功能延期）

- 日期：2026-09-09
- 状态：提议（历史参考）；用户已明确功能延期至上线后，当前不安排方案评审或实现
- 关联：REQ-034、REQ-037、REQ-038、TASK-064；补充ADR-0013

## 当前决定（2026-09-09后续确认）

交接功能不纳入本期MVP和上线阻塞项。本期只接受REQ-038的架构约束：当前负责关系与历史事实分离，稳定业务关联允许未来更换负责人而无需批量迁移下游记录。此约束不等于批准以下交接单、审批、批处理及更正机制，不提前建设完整交接表或接口。下文保留之前的建议供上线后参考，届时按真实需要重新设计。

## 背景与备选

资源方按订单负责人、渠道按门诊负责人划分业务员数据，离职或转交可能影响大量下游记录。方案一逐条修改客户、权益、预约、核销和账单上的负责人，写入多、易漏改且可能污染历史；方案二将旧账号直接变成新员工账号，无法保留身份审计；方案三仅改变根对象当前负责关系，并保留历史事实。推荐第三种。

## 推荐设计

以资源订单/渠道门诊的稳定ID维护当前责任分配，并保存分配历史（原负责人、新负责人、生效时间、交接单、版本）。下游查询从当前责任关系判断跟进权限，不能通过共享客户ID开放该客户其他订单。历史创建人、实际操作者、机构/渠道及核销收益快照不改写。历史业绩归因和当前访问范围分离，具体交接后的历史可见范围需用户评审。

由本机构管理员按冻结对象清单发起，仅同机构有效账号可接收；显示对象数量、待办与权限变化，填写原因并二次确认。资源方可能有很多销售订单，但修改的是负责关系而不是每条患者/权益/交易记录；不承诺任何规模下都是常数成本，也不为此新建无限账号继承链。

提交复核版本与当前负责人，并发已有交接则报告冲突。适量清单同事务变更；大清单分受控批次，每项有状态且可以幂等重试，不静默纳入预览后的新对象。生效后刷新权限和通知接收人，提交业务操作时重查权限。失效授权不能被旧页面、缓存或导出接口绕过。

停用离职账号立即撤销访问，不以完成交接作为停权前置；未交接对象由机构管理员管理。普通在职转交不要求停用原业务员。误交接用新的更正记录，复核当前责任后只恢复仍符合预期的对象，不回滚整库或覆盖期间的新业务、后续转交和财务事实。

## 已确认与未确认

已确认：整张机构结算单由管理员处理，业务员只能看本人明细。上述交接对象、管理员发起、历史可见范围、接收确认及批次机制均为建议，未实现。无需决定正式数据库或增加外部依赖；正式设计需测试权限、事务、失败恢复、审计和负载。

## 验收建议

同机构多订单/门诊定向交接、跨机构拒绝、原费用与创建人不变、清单外对象不变、离职即时停权、缓存失效、并发冲突、分批失败重试、后续业务不被更正覆盖、无整单财务越权。无真实交接测试数据或生产执行。
