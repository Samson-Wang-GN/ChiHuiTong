# 齿慧通软件开发与管理规范

## 1. 目的

本规范用于管理“齿慧通”从需求提出、设计、开发、测试、发布到运行维护的完整生命周期。目标是让每次变更有依据、有负责人、有验证、有记录，并对医疗数据和生产风险保持可控。

## 2. 管理原则

1. **业务价值优先**：每个功能必须对应明确用户、问题和可验收结果。
2. **文档即项目事实**：重要需求、规则和决策以仓库文档为准，聊天记录只作为沟通过程。
3. **小步可逆**：用小变更、独立提交、灰度和明确回滚降低风险。
4. **证据驱动**：测试、日志、截图、检查结果或查询结果支持完成结论；不把推测写成已验证事实。
5. **安全默认开启**：医疗信息、个人信息、权限、导出和外部集成按高风险处理。
6. **简单可维护**：优先已有模式和少量稳定依赖，避免不必要的分布式设计与抽象。

## 3. 角色与责任

| 角色 | 主要责任 | 不可省略的输出 |
| --- | --- | --- |
| 产品负责人 | 明确业务目标、优先级和验收口径 | 需求确认、范围决策 |
| 技术负责人 | 架构、边界、安全、质量和发布决策 | 架构/ADR、风险判断 |
| 开发人员 | 实现、测试、文档和自检 | 代码、测试、变更说明 |
| 测试/验收人员 | 验证业务流程、异常和回归 | 验收记录、缺陷记录 |
| 发布负责人 | 变更核对、备份、发布和回滚协调 | 发布记录、验证证据 |

人员较少时可以兼任角色，但高风险变更应保留非作者复核，不因兼任而省略输出。

## 4. 需求管理

### 4.1 需求准入

每项需求至少包含：

- 稳定编号和标题；
- 背景、目标用户和待解决问题；
- 范围与明确排除项；
- 业务规则、角色与权限；
- 涉及的数据、外部系统和合规影响；
- 可观察、可复现的验收标准；
- 优先级、依赖、风险和待确认项。

不满足准入条件的需求可以进入调研，但不能直接宣称进入开发完成状态。

### 4.2 需求变更

范围、规则或验收口径变化时，先更新需求文档，再调整任务。影响数据结构、接口兼容、安全或发布时间的变更须记录影响分析；重大变化建立 ADR。

### 4.3 优先级

- P0：生产安全、数据泄露、核心业务完全不可用，立即处理。
- P1：关键流程受阻或影响大量用户，优先进入最近修复窗口。
- P2：正常产品迭代，按版本计划交付。
- P3：优化和探索，验证价值后排期。

## 5. 设计与架构管理

- 功能设计先明确领域边界、数据所有权、权限矩阵、状态流转、失败场景和审计要求。
- API 应定义输入、输出、错误、权限、幂等和版本兼容策略。
- 数据模型变更说明新增字段、约束、索引、历史数据处理和回滚限制。
- 外部集成采用适配层隔离，授权凭据按租户和环境管理，并设计超时、限流、重试、去重和降级。
- 关键技术决策采用 ADR；已接受 ADR 不直接改写结论，变化时新增 ADR 并标记替代关系。

## 6. 迭代与任务管理

任务状态统一使用：`待办`、`进行中`、`阻塞`、`待验收`、`完成`。

每个任务包含负责人、关联需求、交付物、验证方法、风险和完成证据。功能按垂直切片拆分，理想情况下每个任务可在较短周期内独立评审和验证。阻塞项需写明阻塞原因、需要谁决定以及解除条件。

建议节奏：

- 迭代开始：确认目标、范围、依赖和验收人；
- 开发期间：及时更新任务状态和新发现的风险；
- 合并前：代码评审与自动化检查；
- 迭代结束：业务验收、文档同步和简短复盘。

## 7. 开发、评审与质量门禁

### 7.1 分支与提交

- 主分支始终保持可发布；功能和修复使用短生命周期分支。
- 一个提交表达一个稳定意图，使用约定前缀并避免混入无关格式化。
- 禁止提交秘密、生产数据、构建垃圾和本地环境文件。

### 7.2 合并请求检查项

- 关联需求和任务；
- 说明用户可见变化与明确未变化部分；
- 列出数据、权限、接口、配置和依赖影响；
- 提供测试命令及结果；
- 提供迁移、部署、监控和回滚说明；
- 确认文档同步且无敏感信息。

### 7.3 最低质量门禁

合并前至少通过项目已配置的格式化、静态检查、类型检查、单元测试和构建。涉及数据库、权限、异步任务、外部集成或核心闭环时，增加对应集成测试和失败路径测试。

## 8. 测试与验收

REQ-040强制执行地点：全部测试运行在公共开发服务器140.143.125.233，本地仅编辑、静态检查及Git操作；不运行本地或GitHub托管Runner测试。GitHub通信由本地承担，服务器接收按提交生成且经过SHA-256校验的文件包，不部署本项目Git仓库/凭据。测试在独立副本和环境进行，记录提交、主机、命令、结果与限制。旧本地验证记录不代表后续获准本地测试；详见[开发环境](operations/development.md)。

测试分层包括：

- 单元测试：业务规则、状态转换和纯逻辑；
- 集成测试：数据库、接口、权限、任务队列和外部适配层；
- 端到端测试：最关键的用户业务闭环；
- 冒烟测试：每次部署后快速确认服务与核心路径；
- 安全与隐私测试：越权、租户隔离、敏感信息泄露、导出和审计。

缺陷至少记录复现步骤、实际结果、预期结果、环境、严重度和相关证据。修复缺陷时优先补充能复现问题的自动化测试。

业务验收以需求文档中的验收标准为准。由于环境或权限无法验证的部分必须列为验证限制，不得自动视为通过。

## 9. 发布与变更管理

### 9.1 发布前

- 明确版本、变更范围、负责人和时间窗口；
- 检查自动化门禁、配置差异、依赖和数据库迁移；
- 对数据库和目标文件执行可恢复备份，并验证恢复路径；
- 准备逐步发布、兼容窗口、监控指标和回滚条件；
- 高风险发布获得产品、技术和发布责任人确认。

### 9.2 发布中

- 使用可重复的自动化流程，记录版本和执行结果；
- 数据库采用向前兼容的分阶段迁移；
- 不在生产服务器直接进行未记录的临时编辑；紧急修复也要回补仓库和文档。

### 9.3 发布后

- 检查进程、依赖、迁移、关键页面与接口、异步任务和错误日志；
- 完成至少一个真实但不泄露敏感数据的核心业务冒烟流程；
- 观察关键错误率、延迟和业务指标；达到回滚阈值立即止损；
- 在 `docs/tasks.md` 或发布记录中写明版本、证据、异常和遗留风险。

## 10. 安全、隐私与合规管理

- 建立角色权限矩阵，服务端按租户和资源范围鉴权，默认拒绝未明确授权的访问。
- 敏感数据传输和存储采用适当加密；密钥独立管理并定期轮换。
- 敏感操作记录操作者、时间、对象、动作和结果，审计日志避免记录敏感正文。
- 数据导出设置权限、范围、用途、有效期和审计，默认水印或可追踪标识。
- 第三方处理数据前明确授权主体、处理目的、字段范围、保存期限、安全责任和退出删除方式。
- 漏洞或泄露疑似事件立即限制影响、保全证据并按事故流程升级，不在公开渠道传播敏感细节。

## 11. 配置、依赖和资产管理

- 配置按环境分离，变量在 `.env.example` 和 README 中登记，秘密不入库。
- 新依赖需说明用途、维护状态、许可证、安全风险、体积和替代方案；锁定可复现版本。
- 定期检查过期和高危依赖，但升级应独立验证，不与无关功能混合。
- 数据库结构、接口契约、部署脚本和监控配置与应用代码一起版本管理。

## 12. 事故与问题管理

事故处理顺序为：确认影响、止损、保全证据、恢复服务、验证业务、沟通状态、分析根因、落实改进。

P0/P1 事故应形成复盘，包含时间线、用户和数据影响、直接原因、系统性原因、处置过程、哪些监控失效、纠正措施、负责人和截止时间。复盘关注系统改进，不以追责替代根因分析。

## 13. 度量与持续改进

早期项目只保留能指导行动的指标：需求交付周期、发布频率、变更失败率、恢复时间、线上缺陷、自动化测试稳定性和核心业务成功率。指标用于发现流程问题，不用于鼓励拆提交、隐瞒缺陷等行为。

每个阶段性版本结束后复盘一次：保留有效做法，删除无价值流程，把重复问题转为自动化检查或明确规范。

## 14. 文档与记录保留

需求、ADR、测试证据、发布记录和事故复盘应与版本关联。文档只记录必要信息，不嵌入患者数据和秘密。过期规则应标记替代关系或删除，避免多个冲突版本并存。

## 15. 首个版本启动门槛

进入首个功能开发前，应至少完成：产品定位与用户确认、MVP 范围、核心业务闭环、初始角色权限矩阵、数据分类、技术栈 ADR、环境与分支策略、基础 CI、测试策略和发布/回滚草案。
