## 2. 产品定位

“齿慧通”是连接客户资源方、口腔门诊渠道方、口腔门诊和终端客户的口腔福利履约与门诊拉新平台。

平台通过承接保险、银行及其经纪代理公司的客户福利投放，把不记名权益卡或已分配给指定客户的口腔优惠权益，与门诊代理公司所服务的口腔门诊进行匹配，完成“权益投放—客户激活/领取—查找门诊—预约—到诊—核销”的业务闭环，为口腔门诊带来可追踪的获客与到诊业务。

本产品当前不是口腔诊疗管理系统，不以保存完整电子病历、处方或治疗过程为目标。

## 3. 业务目标

1. 让客户资源方既能通过不记名卡批次面向未知客户投放福利，也能通过 Excel 批量导入指定客户及其福利权益。
2. 让终端客户注册绑定后扫码激活不记名卡，或领取已经通过 Excel 分配到本人名下的福利，再查找适用门诊并完成预约。
3. 让门诊渠道公司高效签约、开通和管理合作门诊。
4. 让口腔门诊获得稳定、可核验、可追踪的客户到诊来源，但当前不判断客户是否属于“新客”。
5. 让平台统一管理优惠规则、机构权限和完整履约数据，避免错误入账、重复导入、越权修改和虚假核销。
6. 门诊核销后按合同周结/月结收取获客费，以付款凭证审核或微信扫码支付完成收款，不设置授信。

## 5. 业务角色

### 5.1 平台管理员

- 管理客户资源方、门诊渠道公司、口腔门诊和后台账号；
- 审核机构与门诊资料；
- 创建、修改、启停推广产品；
- 管理平台—资源方和平台—渠道合同及方案授权，审核渠道提交的门诊三方合同/续签，并按有效合同控制业务权限；
- 审核门诊资质、三方合同、结算周期和变更版本，查看全部照片/附件；授信、调额及额度冻结流程取消，门诊运营暂停权限保留；
- 核实资源方采购付款，审核销售订单及资源方填写的采购价，通过后开卡；实体卡线下制作寄送；
- 审核门诊结算凭证并确认实际到账；
- 查看全平台业务数据和审计记录；
- 处理需要平台介入的异常、冻结、撤销与申诉。

### 5.2 客户资源方

- 管理本机构后台账号；
- 以 Excel 形式上传本机构客户资料、对应福利权益及数量；
- 提交不记名权益卡批次购买/开卡申请，在平台确认线下业务依据后下载或打印本机构卡片二维码；
- 只能从平台为本机构配置的权益来源展示名列表中选择展示名；
- 查看本机构 Excel 导入和不记名卡产生的权益、预约、到诊和核销数据；
- 当前不提供逐个选择客户购买并赠送权益的功能，该模式保留为后续需求；
- 只能访问本机构与客户的关系及本机构来源权益，不能查看、推断或修改其他资源方与同一客户的关系和权益。

### 5.3 门诊渠道公司

- 管理本机构后台账号；
- 录入、提交并维护本机构签约门诊资料；
- 为每家门诊指定具体负责业务员；负责业务员必须具有渠道公司后台账号并绑定手机号；
- 在门诊管理中组织三方合同签订/续签、上传完整资料及管理优惠上下线；负责业务员查看账单并催收，不承担担保责任；
- 为签约门诊申请开通齿慧通服务；
- 在平台已有推广产品中，为所管理门诊选择上线或下线；
- 查看本机构签约门诊产生的预约、到诊和核销数据；
- 不能创建或修改平台推广产品。

### 5.4 口腔门诊

- 管理本门诊资料和后台账号；
- 在平台已有推广产品中选择本门诊上线或下线；
- 接收待确认预约，与客户沟通后确定最终预约日期和时间；
- 查看本门诊应付、账单及收款进度；授权人员可上传付款凭证或微信扫码支付，但不能确认线下到账；
- 工作台展示待付款、凭证退回、支付待确认及逾期提示，不显示信用余额；逾期仅提醒，由平台人工决定上下线；
- 查看本门诊必要范围内的客户预约信息；
- 客户到诊并完成服务后核销相应客户权益数量；
- 使用独立门诊端小程序在手机上完成现场权益核验、核销、错误核销撤销并查看本门诊业务数据；
- 查看本门诊业务数据，不能访问其他门诊数据；
- 不能创建或修改平台推广产品。

### 5.5 终端客户

- 通过齿慧通小程序使用手机号注册和登录；
- 完成身份验证并绑定系统内已有的本人客户档案；
- 登录或绑定后检查并领取已记入本人客户档案的待领取权益；
- 查看本人待领取及已领取权益的数量、来源、适用范围和有效期；
- 授权定位后搜索附近适用门诊；
- 提交、查看和管理本人预约；
- 到诊时向门诊出示核销凭证；
- 查看本人权益使用记录。

> 说明：机构与账号是两个层次。同一机构可以有多个操作账号；账号权限必须受所属机构和角色共同限制。客户档案是平台级身份，不是客户资源方的租户私有对象；资源方隔离边界落在客户资源关系、导入数据和权益来源上。

## 6. 核心业务流程

### 6.1 记名非实体卡销售与权益履约流程

1. 平台管理员预先配置并启用推广产品。
2. 客户资源方进入推广产品销售，选择记名非实体卡及批量客户/单个客户。批量上传Excel资源方客户编号（选填）、姓名、手机号和开卡数量，以及性别/年龄/职业可选资料；单客填写同类字段。订单统一选择授权推广产品、来源展示名、每卡份数和采购单价（默认0元）。
3. 系统校验文件和明细、汇总张数和采购总金额，生成销售订单。零元直接待审核；非零先由资源方付款并上传凭证，平台确认全额实际到账后才待审核。错误明细不能提交。
4. 平台审核销售订单的授权、来源、采购价、客户资料和有效期（默认180天，可修改）；通过前不创建关系或待领取权益。审核拒绝记录原因，已收款订单进入线下退款登记，改价或修正资料应另单提交。
5. 审核通过后，系统在平台客户范围内按已确认的唯一匹配规则查找客户档案：即使客户已与其他资源方有关联，匹配成功时仍使用同一平台客户档案；匹配失败时自动创建“未注册/未绑定”的客户档案。
6. 系统为本次导入建立“当前资源方—客户”的独立客户资源关系；已有相同关系时复用，不因其他资源方已经关联该客户而拒绝导入。
7. 系统将明细中的推广产品和数量以“待领取”状态记入对应客户档案，并强制保留来源资源方、客户资源关系、导入批次、导入明细及平台审核确定的有效期天数。不同资源方提供的权益不得因客户和方案相同而合并成无法区分来源的一笔权益。
8. 权益分配不以客户注册为前提。客户每次登录小程序或首次注册绑定手机号后，系统先检查待领取权益；存在时提示领取，客户也可稍后从“待领取优惠”中主动领取。
9. 客户领取后，权益从待领取变为可使用，并以领取成功时间为有效期起点，按批次审核通过的有效期天数计算到期时间；领取操作不新增权益数量，但会使该权益所属导入批次不可回滚。
10. 客户授权定位或选择地区，搜索资质/合同有效、服务正常且已上线对应优惠的门诊，不校验信用或风险余额；逾期仅提醒，由平台人工处理，不自动限制搜索或预约。
11. 客户选择具体来源权益、门诊和意向时间，提交时复核权益数量、授权及门诊资格，原子占用权益，不计费或建立风险金额。
12. 系统向门诊预留的预约联系手机号发送短信，并在门诊后台工作台突出显示待确认预约。
13. 门诊与客户沟通后确定最终预约日期和时间并确认预约；预约确认保存单次核销数量，不锁定费用或分配；核销时锁定费用/分配且产生应收。门诊渠道公司不能代门诊处理预约。
14. 客户收到确认结果并可查看最新状态；客户或门诊按规则取消预约时，系统按REQ-030判断是否释放预约占用权益。核销前未计费，取消不产生费用冲销。
15. 客户按预约到诊，向门诊出示对应权益的固定二维码。
16. 门诊员工使用独立门诊端小程序扫码并实时查询服务端状态，在完成约定服务后按方案快照核销固定数量的权益；系统记录权益来源、门诊、预约、操作人、核销时间、核销数量和操作终端，并在核销成功时记入获客服务费应收和三方收益明细。
17. 系统按门诊三方合同周结/月结出账；门诊上传付款凭证经平台审核，或微信扫码支付经服务端核实成功，全额收款后结清账单。
18. 每个客户资源方只能查看归属于本机构来源权益的客户完整字段和履约结果；其他参与方按各自权限查看。

### 6.2 不记名权益卡履约流程

1. 客户资源方选择不记名实体卡，无需Excel或客户资料；填写数量，选择本机构授权推广产品、来源展示名、每卡份数及单卡采购价，默认0元，提交销售订单。
2. 系统保存采购价和数量快照，总额=采购单价×张数；零元直接待审核，非零先待付款、上传凭证并由平台确认全额实际到账，再进入待审核。平台审核价格而非静默改价，有效期默认180天且可修改。
3. 平台审核通过后生成批次、卡号及不重叠号段登记，重复审核不重复生成、取消后号段不复用。公开卡号可连续，激活凭证必须独立随机不可猜测，不以号段作为激活密钥。采购款线下支付，不扩展在线支付或发票；门诊账单在线支付见REQ-016。
4. 平台在线下制作实体卡并邮寄给购买方，系统记录制作、寄送状态和必要的寄送凭据；资源方再在线下发放实体卡。
5. 不记名卡激活前不创建客户档案、不要求客户姓名或手机号、不设置激活截止日期；卡在激活前可以由资源方交付给任意客户，平台不记录资源方的具体发放对象。
6. 客户使用微信扫描卡片二维码进入客户端小程序；未登录时先完成手机号注册或登录，随后查看推广产品、来源展示名、激活后有效期天数和必要使用条件并确认激活。
7. 系统在同一事务中校验卡片有效、未激活、未作废、未冻结及当前客户身份，将卡绑定至当前客户档案，建立或复用客户资源关系，并生成可使用权益；权益从激活成功时间开始按开卡订单确定的有效期天数计算到期时间，同一卡片只能成功激活一次。
8. 激活后，卡片与客户权益永久保留关联，客户可使用小程序中的固定权益二维码，也可携带原卡到门诊；门诊扫码后仍必须由服务端校验权益所有人、有效预约、状态、适用范围和门诊权限。
9. 已激活卡片不能转让或被其他客户再次激活；其他人扫描时只返回不可用提示，不展示已激活客户的身份、权益或预约信息。
10. 客户使用该权益完成门诊搜索、预约、确认、到诊、核销和门诊账单结算，后续流程与 Excel 来源权益一致。

### 6.3 门诊入驻、三方合同与优惠上线流程

1. 渠道公司在“门诊管理”中新增门诊，填写主体、持证经营地址、联系人、负责业务员、资质及展示照片。
2. 渠道公司负责组织平台、渠道公司、门诊三方签约，在同一门诊详情的“合同与续签”区块登记三方合同并上传完整签署附件；不再分别新建渠道—门诊、平台—门诊两份双边业务合同。
3. 门诊资料与合同可一并提交，但审核结论分别记录；平台审核时必须能查看本次提交的所有照片和附件，以及对应合同版本。
4. 平台通过后，系统按资质、有效平台—渠道合同、有效门诊三方合同和门诊服务状态校验上线条件。三方合同不含授信字段，结算周期为必填周结/月结。
5. “门诊管理 → 具体门诊 → 推广产品”默认列出当前渠道全部可用方案；无需逐项添加授权关系，尚未选择上线的方案默认下线。
6. 渠道或门诊可上线/下线门诊优惠；上线须满足现有授权和服务条件，下线不受新增业务条件限制。操作不需要平台逐项审核。
7. 仅审核通过、合同有效、服务正常且相应优惠已上线的门诊可被搜索和新预约；取消所有额度和待履约风险金额校验。逾期仅提醒，由平台人工决定是否下线。
8. 续签从原门诊进入，预填三方主体并创建新版本；平台审核通过且到达生效时间后替换旧有效版本，保留历史。存量预约按既有规则履约。

## 7. 功能需求清单

### REQ-001 建立项目开发与软件管理规范

**目标**：建立统一、可执行、可追踪的研发和管理基线。

**状态**：已完成。

**验收标准**：项目开发、需求、架构、任务、测试、安全、发布和技术决策规则均已有仓库文档承载。

### REQ-002 多机构、用户与权限管理

**目标**：支持多类机构及其账号安全登录后台，并严格隔离业务数据。

**需求清单**：

- 支持客户资源方、门诊渠道公司、口腔门诊三类业务机构，以及平台运营主体；
- 客户资源方固定细分为保险公司、银行、经纪代理公司三种机构类型，当前不提供机构类型配置功能；
- 支持机构启用、停用、审核中和审核不通过等状态；
- 一个机构可创建多个后台账号，并可停用单个账号；
- 门诊可为获授权员工开通独立门诊端小程序身份，员工身份必须绑定具体门诊和权限；
- 支持平台管理员、机构管理员和机构业务操作员等基础角色；
- 所有服务端接口同时校验账号权限、所属机构和数据范围；
- 客户档案不设置唯一客户资源方归属；系统使用独立关系表达一个客户与多个资源方之间的多对多关系；
- 资源方的数据权限以客户资源关系、导入批次和权益来源为边界，而不是以客户档案所有权为边界；
- 关键登录、授权和业务操作保留审计记录；
- 被停用的机构或账号不得继续访问受保护功能。

**验收标准**：两个客户资源方导入同一个自然人时，系统只关联一个平台客户档案、分别建立两条客户资源关系并保留两方权益来源；任一资源方均无法读取或修改另一方的关系、导入、权益和履约明细。

### REQ-003 推广产品管理

**目标**：由平台统一配置多种口腔优惠，而不是把系统限定为洗牙券。

**需求清单**：

- 平台管理员可创建免费服务券、折扣券、定额抵用券等推广产品；
- 推广产品至少描述稳定产品编号、内部展示名称、外部产品展示名称、展示说明、权益类型、权益价值、适用项目、使用条件、默认有效期天数、核销规则和状态；两个名称必填，展示范围及改名规则见REQ-026，默认有效期为180天；
- 每个推广产品配置固定单次核销数量和固定单次获客服务费；默认一次预约核销 1 份权益并产生 1 次获客服务费。合作方使用授权及分配规则不在全局方案中统一设置，而在各合作方合同中按方案配置（REQ-020）；
- 合作方收益支持按比例或固定金额配置，校验完整三方分配与获客服务费一致；费用/分配在核销事务中锁定，之后的变更不改写已核销历史；预约确认不锁定费用；
- Excel 导入批次和开卡申请审核时均保存本次有效期天数，默认取 180 天且平台可修改；Excel 权益从客户领取成功时间起算，不记名卡权益从客户激活成功时间起算；不记名卡不设置激活截止日期；
- 平台管理员可启用、停用推广产品；
- 已被发放或使用的历史优惠规则必须保留，不应因后续编辑而被静默改变；
- 客户资源方的导入文件只能引用平台允许该机构使用的方案，不能在后台逐客发放或修改方案规则；
- 平台按客户资源方维护相互隔离的权益来源展示名列表；资源方在 Excel 批次和开卡申请中只能选择本机构列表中的启用项，不能查看、选择或新增其他资源方的展示名；
- 渠道公司和门诊只能选择是否上线平台方案，不能修改方案规则；
- 系统记录方案创建、修改、启停和适用范围变更。

**验收标准**：至少能用同一套通用模型配置“洗牙券”和“种植牙/正畸抵用券”，且非平台管理员无法更改其规则。

### REQ-004 Excel 客户资料导入、客户匹配与权益入账

**目标**：让客户资源方通过 Excel 批量导入客户资料及其福利，由系统自动匹配/创建客户，并将权益以待领取状态分配到客户名下。

**需求清单**：

- 本需求作为REQ-028记名非实体卡批量客户录入的子流程；后台单个客户同样遵循匹配/领取规则，不新增绕过订单审核的手工发放。小程序单客购买赠送仍延期；
- 提供标准 Excel 模板、填写说明和可下载示例；同时按REQ-041支持机构自有列名、顺序、工作表及表头行，不强制套用标准模板；
- Excel模板包含资源方客户编号、姓名、手机号、开卡数量；姓名、手机号和数量必填，资源方客户编号选填，仅作资源方原始资料留存，不参与客户匹配或任何系统关联。数量可以按明确映射的列读取，也可由操作人明确选择统一数量并填写正整数；禁止隐式补1，按列读取的空值仍报错。推广产品、来源展示名、每卡权益份数及采购价在订单级统一选择，不逐行混合不同产品；
- 平台客户编号由系统在创建客户档案时自动生成，平台内唯一且稳定，导入文件和人工录入不能指定或覆盖。权益、预约等内部关联使用系统客户标识，不使用资源方客户编号；匹配已有客户时保留其系统编号；
- 资源方客户编号属于来源资料，保存在相应资源关系及订单明细快照中，不作为客户全局属性覆盖其他来源。相同外部编号不能合并不同手机号客户，不同或空外部编号不能拆分手机号和姓名一致的客户；即使外部编号恰好等于平台编号，也不能据此关联。同一机构内也不将外部编号用作客户唯一键或导入去重键；
- 权益来源展示名用于客户端展示，可以是实际保险公司等品牌名称且不强制等于上传机构名称，但资源方只能选择本机构的来源展示名列表，不能在 Excel 中自由新增名称或引用其他资源方的配置；
- 来源展示名随客户权益保存为历史快照，后续修改资源方名称不得静默改变已经分配权益的客户展示；平台后台仍保存并可审计实际来源资源方；
- 上传及提交时只校验和预览匹配，不写客户或权益；提交形成销售订单，零元待审核、非零确认全额到账后待审核。审核时复核匹配和有效期（默认180天，可修改），通过后原子创建关系及权益；
- 上传前提示数据用途和授权责任，上传后进行格式、必填项、有效合同、方案权限、来源展示名权限和重复数据校验；
- 每次上传生成独立批次，展示成功、失败和重复数量，并提供逐条错误原因；
- 手机号是平台客户的唯一主匹配字段；导入前先统一手机号格式，至少清除空格和分隔符并统一中国大陆国家码表达，无法规范为合法手机号的明细作为异常数据处理；
- 每条有效明细独立处理：规范化手机号未命中时自动创建未注册/未绑定客户档案；手机号命中且姓名经过基础去空格后相同时关联现有客户；手机号命中但姓名不一致时不得匹配、不得新建同手机号客户，整条明细进入异常数据；
- 客户匹配在平台客户范围内进行，不局限于当前资源方；命中其他资源方已关联的客户时复用同一平台客户档案，并为当前资源方建立独立客户资源关系；
- 同一个客户可以与多个资源方同时关联，客户档案不得设置排他的资源方归属；
- 手机号和姓名不一致的异常不进入平台审核更新或客户本人验证流程，由资源方修正 Excel 后重新导入；
- 平台审核通过且客户匹配/创建完成后，按订单推广产品、明细开卡数量及每卡份数生成待领取权益，记录销售订单、明细、来源关系及审核确定的有效期天数；
- 每项客户权益强制关联且只能关联一个来源资源方；同一客户、同一推广产品来自不同资源方时分别记账、分别计算余额和分别归因；
- 客户是否已经注册绑定不影响权益入账；
- 失败明细不得创建客户、增加权益或产生半完成数据；
- 同一批次内的处理任务和系统重试必须幂等；不同上传批次暂不区分资源方追加权益和重复文件/重复明细，每个成功上传按独立批次处理；
- 每个批次记录状态、导入时间、审核人、审核时间、有效期天数、文件摘要、成功/失败数量、权益数量和领取情况；
- 记名订单整批回滚统一通过申请整单取消、平台审核后使权益失效；不删除采购/收款事实，已收款需线下退款登记。不支持部分回滚，全部权益均未领取才允许；
- 批次中任一权益已经领取，即使尚未预约或核销，整批也不得回滚；系统应明确展示阻止回滚的原因和已领取数量；
- 批次回滚与客户领取必须互斥并保持事务一致性，不能出现检查时未领取、回滚过程中又领取成功的竞态；
- 成功回滚后，该批次产生的待领取权益全部失效并保留回滚审计；不得删除平台客户档案、其他批次权益、其他资源关系或其他来源权益；
- 已有权益被领取而不能整批回滚时，资源方可申请“停止批次剩余权益”，平台审核；系统只使该批次尚未领取的剩余权益失效，已领取权益不得被自动收回，并进入后续异常处置范围；
- 停止批次剩余权益与客户领取必须互斥且幂等，保留申请人、原因、停止数量、已领取数量、处理时间和完整审计；该操作不得伪装成整批回滚；
- 已入账权益的来源必须追溯到客户资源关系、客户资源方、导入批次和具体明细；
- 面向资源方返回导入结果时，不得暴露该客户是否同时属于其他资源方、其他来源权益或其他资源方的外部客户编号；
- 客户资料仅用于客户匹配和约定业务用途；资源方在本方关系范围可见完整字段，其他参与方按REQ-011脱敏；
- 导入、匹配、建档、入账、查询、导出和作废/冲正均记录操作审计；
- 普通资源方账号不得绕开导入批次直接修改客户权益数量。

**验收标准**：使用两个具有有效合同的资源方分别选择本机构来源展示名并导入包含重叠客户的数据，同时覆盖已有已绑定客户、已有未绑定客户、新客户、手机号格式差异、手机号与姓名冲突及错误明细。审核前不产生客户关系或权益；平台以默认 180 天或修改后的天数审核通过后，系统规范手机号、复用匹配客户的平台档案、隔离两方资源关系并创建待领取权益；客户领取时从领取成功时间开始计算到期时间。同批任务重试不重复入账；全批未领取时可回滚，任一权益领取后整批不可回滚但可停止尚未领取的剩余权益；停止与领取并发时不得错误领取或扩大失效范围；资源方看不到对方关系和权益；每笔权益均可追溯至本方原始导入明细。

### REQ-005 小程序注册、客户档案绑定、权益领取与卡激活

**目标**：让终端客户安全绑定平台客户档案，领取 Excel 已分配权益，或扫描不记名卡并将权益激活到本人名下。

**需求清单**：

- 终端客户在客户端小程序通过微信手机号授权完成注册或登录；后台账号采用手机号+短信验证码登录；
- 客户端优先使用微信授权的默认绑定手机号完成注册或登录；平台已有同手机号客户档案时直接绑定，不存在时创建无权益的已注册客户档案，后续资源方导入时再按手机号匹配；
- 首次使用时展示并记录必要的用户协议和隐私授权；
- 系统使用微信授权确认后的规范化手机号查找唯一客户档案并完成账号绑定；姓名一致性保护仅用于资源方 Excel 导入匹配，不用于阻止手机号持有人登录或绑定；
- 绑定操作只建立账号与客户档案的关联，不新增、不复制权益；
- 账号绑定必须幂等，同一客户档案不得被多个无权账号重复绑定；
- 客户通过不记名卡二维码进入小程序时，必须先完成登录和手机号身份绑定，再执行卡激活；仅打开二维码页面不得改变卡片或权益状态；
- 激活前向客户展示推广产品、权益来源展示名、每卡权益数量、激活后有效期天数和必要使用条件，并明确卡片不设置激活截止日期，由客户主动确认；
- 卡激活以当前已登录客户为归属对象，不执行 Excel 的手机号与姓名匹配；系统为当前客户建立或复用该资源方关系，并使卡片权益直接进入可使用状态；
- 卡激活必须原子且幂等；并发扫描、重复点击或网络重试时，同一卡只能归属首个成功激活的客户，其他请求不得新增权益或暴露首个客户信息；
- 每次登录以及首次注册绑定成功后，系统检查该客户档案下的待领取权益；存在时显示明显提示和领取入口；
- 客户也可以稍后进入“待领取优惠”列表，逐项查看权益来源展示名、方案、数量、限制和领取后有效期天数并完成领取；
- 领取只将已分配权益从待领取激活为可使用，不增加权益数量，并记录领取人、领取时间、来源批次及按领取时间计算的到期时间；
- 领取操作必须幂等，重复点击或网络重试不得重复增加可用数量；
- 领取成功后，来源导入批次立即进入不可回滚状态；
- 客户本人可以查看名下来自多个资源方的待领取及已领取权益；相同方案的不同来源权益仍保持可区分，预约时应明确使用哪一笔已领取权益；
- 不向客户展示其他客户档案或其他人的任何信息；
- 平台手机号必须唯一，不应出现多个候选客户档案；
- 未经受控身份核验，不得自动合并多个客户档案或转移权益；
- 客户可以修改本人姓名等允许维护的客户资料，但不能在小程序中修改绑定手机号；
- 客户可查看本人的待领取、可使用、预约占用、部分使用、已用完、已过期或已失效权益。

**验收标准**：已验证用户只能绑定与本人微信授权手机号唯一对应的平台客户档案；没有既有档案时可创建客户并正常登录；登录后能领取各资源方通过 Excel 分配的待领取权益，也能扫描未设置激活截止日期的有效不记名卡并主动确认激活；两种权益均从领取或激活成功时间起按审核确定的天数计算到期时间。同一卡在并发和重试情况下只产生一笔归属明确的权益，已激活、作废或冻结卡不能再次激活且不泄露原持有人信息；领取前 Excel 来源批次可回滚，领取后整批不可回滚；客户可修改允许的个人资料但不能修改手机号。

### REQ-006 门诊入驻、审核与服务开通

**目标**：渠道公司在门诊管理中完成入驻资料、三方合同签订/续签及服务准备，平台统一审核。

- 一个持证经营地址视为一家门诊；同一主体可有多个门诊，但每家门诊独立审核、合同和账单。
- 门诊资料至少包括名称、主体、地址、定位、联系人及手机号、预约联系手机号、营业信息、展示照片、营业执照、医疗机构执业许可证和负责业务员。
- 门诊三方合同由平台、当前渠道公司、门诊共同签订；渠道负责签订资料登记、附件上传、提交和续签，平台负责审核；门诊可查看本门诊合同，不自行审核或替换合同。
- 合同至少记录编号、三方主体、签订日期、生效/到期日期、周结/月结、付款责任主体、收款主体、财务联系人及手机号、签署附件、版本和审核信息。不填写授信额度、风险上限或调额参数。
- 三方主体引用对应机构/门诊记录，不能用自由文本冒充其他机构；提交时核验关联和资料完整性，合同审核生效前相关主体资质必须通过。日期先后合法，每家门诊同一时点只允许一份已审核有效三方合同。
- 允许保存草稿；资料与合同分项审核并展示结论，不能因其中一项通过直接上线。门诊资质完整资料审核时限仍为2个工作日；退回须说明具体字段/附件原因，补齐后重新计算。
- 所有门诊相关审核入口（入驻、资质变更、合同首签及续签）在当前页面内展示本次提交全部照片和附件及数量、类型、名称、版本；图片缩略图可放大逐张查看，PDF可预览，其他允许格式可授权下载。失败项明确显示并可重试，必需资料无法读取时不得通过审核；不以仅显示文件名代替查看。
- 门诊通过主体审核后可开通受限账号准备上线；只有资质、有效三方合同、有效渠道合作合同、服务状态和优惠授权满足时才能承接新预约。运营停用与授权停用保留，但不使用授信冻结流程。
- 渠道从门诊详情发起续签/合同变更；待审核新版本不覆盖仍有效旧版本，拒绝保留原因和旧版本。新版本生效时保证期限不冲突；已核销费用和预约履约信息不改写，未核销费用按REQ-037锁定。
- 周结/月结和付款期限沿用REQ-016；结算周期经原合同变更权限审核生效后立即应用，不追溯已出账单；未出账交易按新账期出账，见REQ-037。
- 合同到期前30天在门诊及渠道负责业务员工作台提醒。到期、暂停或退出阻止新预约，但存量待确认/成功预约保留必要确认、改期、核销权限；确实无法接诊时由门诊逐条取消并通知客户，权益按REQ-030处理。
- 每家门诊仅归属一个渠道；变更必须先下线，由平台办理后再上线。新渠道三方合同通过并生效前不得承接新预约；不静默替换旧合同签约方，历史业绩和费用快照保留。

**验收标准**：在一个门诊上下文内完成资料录入、所有附件查看、三方合同提交/退回/审核、续签及上线准备；没有任何额度必填或额度审批。其他渠道不能访问该门诊或附件；缺失/不可读必需附件、无有效合同或续签未生效不能绕过上线校验，存量履约和历史版本不丢失。

### REQ-007 门诊优惠上线管理

**目标**：将门诊优惠配置整合进门诊管理，不再要求渠道先在独立菜单逐条添加门诊方案。

- 主入口为“门诊管理 → 具体门诊 → 推广产品”；表头常驻门诊名称、所属渠道和授权来源合同摘要，不在操作中反复选择门诊。
- 默认“全部”列出该渠道当前有效平台合同下全部启用授权且全局启用的方案，包括尚未为本门诊上线的方案。新授权自动进入可选列表但默认下线，不自动替门诊承诺服务。
- 列表显示内部展示名称、服务内容、使用条件、单次核销数量、单次获客费、授权可用性、本门诊上线状态和操作。无需另行“新增/添加推广产品”才能看到可用方案。
- 状态Tab按本门诊的全部/已上线/已下线展示，零记录保留；授权有效性作为独立标签和限制原因，不冒充上线状态。曾使用而现已失去授权的方案留在历史或受限记录中可追溯，不算当前可用方案。
- 渠道只能操作所管门诊，门诊仍可操作本门诊；只允许上线/下线，不得更改规则、费用或上游授权/分配。
- 上线时服务端复核有效渠道合同、方案授权、门诊三方合同、资质及服务条件；下线随时可做。上下线无需平台再次审核，不设置门诊配额、每日限额或提前下线限制。
- 优惠下线、全局方案停用或上游授权失效后停止新预约；保留已入账客户权益及存量预约的履约记录，恢复授权不自动替代门诊的主动下线选择。
- 门诊无授信和风险余额校验；逾期本身不自动下线，由平台人工操作并记录原因。

**验收标准**：渠道有3个可用方案而门诊尚未配置时，默认显示3条已下线记录，可在同页上线/下线；增加上游授权自动出现可选记录。切换门诊不会带入上一门诊状态，返回列表保持筛选和位置。越权或失效授权不能上线；下线和历史履约不受影响。

### REQ-008 附近门诊搜索与详情

**目标**：帮助客户找到能够承接本人权益的合适门诊。

**需求清单**：

- 客户可授权定位，拒绝定位时可手动选择城市或区域；
- 默认只搜索可承接所选权益、审核通过、合同有效且服务正常的门诊，不使用金额风险门槛；逾期仅提醒，由平台人工处理，不自动限制搜索或预约；
- 结果展示门诊名称、地址、距离、营业信息、可用优惠和必要的预约提示；
- 支持按距离和区域筛选，其他排序规则待确认；
- 门诊详情展示门诊资料、适用优惠、使用条件和预约入口；
- 未经用户授权不得获取精确位置，位置数据按最小必要原则使用。

**验收标准**：客户选择一张可用权益后，只能看到并预约当前可承接该权益的有效门诊；门诊临时下线后立即退出搜索和新预约范围，限制解除且无其他下线原因时自动恢复。

### REQ-009 预约管理

**目标**：建立客户与门诊之间可追踪的到诊安排。

**需求清单**：

- 客户从本人可用权益进入门诊预约；
- 每条预约必须关联一个指定来源的已领取优惠权益，并在预约期间占用相应权益数量；
- 客户提交预约只占用相应客户权益，不生成待履约风险金额、信用占用或应收；核销前取消不计费，权益是否释放按REQ-030；
- 预约同时保存客户提交的意向日期/时间与门诊最终确认的预约日期/时间，不得用最终时间覆盖客户原始意向；
- 客户提交后进入“待确认”；不要求门诊预先配置可预约时段。门诊与客户沟通后填写最终预约日期和时间，并将预约确认成“成功”；
- 门诊确认预约时保存固定单次核销数量，不锁定费用；获客费与分配在核销时锁定，不校验授信上限；
- 最终预约日期不得晚于关联权益到期日期；任何预约改期也必须重新校验，不能改到权益到期日之后；
- 每个门诊配置一个预约联系手机号；新预约提交成功后，系统向该号码发送短信通知；
- 门诊后台工作台显著展示待确认预约数量、列表和超时情况，门诊登录后无需进入深层菜单即可处理；
- 门诊Web后台按REQ-039默认随主动登录开启预约提醒小窗，工作台保留“开启预约提醒”；与原短信和独立待处理任务页共同提醒，不替代它们。
- 每家门诊由平台配置独立的待确认处理时限，默认为 24 小时，门诊及渠道不可编辑；待确认预约超过该时限仍未确认时，系统自动以“待确认超时”原因为取消并释放权益占用；
- 门诊渠道公司只能查看签约门诊的预约数据，不能代门诊确认、取消、改期或核销；
- 客户和门诊均可查看与自身相关的预约及状态变化；
- 门诊有预约处理权限的员工可以在预约详情查看客户用于本次预约的完整手机号，以便双方自行沟通时间；该手机号不得因此出现在无关客户列表或超出预约业务范围的导出中；
- 同一客户权益的有效预约占用数量不得超过当时可用数量，避免超额预约；
- 预约业务状态只使用：`待确认`、`成功`、`完成`、`取消`；不设置“已到店”“已拒绝”或独立“爽约”状态；
- 客户可以在客户端小程序主动取消待确认预约或尚未到最终确认时间的成功预约；门诊无法承接时可对同一范围以“无法接诊”取消。成功预约时间已过时，双方通过REQ-030反馈/申请处理，不得从普通取消入口直接释放；渠道公司不能取消；
- 客户和门诊均可对成功预约发起改期，但两类操作的生效机制不同；
- 客户在客户端小程序发起改期时，系统创建一条“改期待确认”请求，不立即修改当前有效预约时间；门诊确认后才以新时间替换当前预约时间并保持预约为成功，门诊拒绝或改期请求超时则原预约时间继续有效；
- 客户改期请求的处理时限复用本门诊待确认处理时限，默认 24 小时；界面必须明确提示客户“门诊确认前改期尚未生效”，并向门诊发送待办和通知；
- 门诊发起改期时，系统必须提示并要求操作人确认“已与客户协商一致”；未确认协商一致时不得提交。确认后新时间直接生效并通知客户；
- 所有改期均须校验新时间不晚于权益到期日，记录原时间、新时间、发起方、确认方、协商确认、操作时间和结果；同一预约同一时间只允许一条有效改期请求，重复提交或并发确认不得重复改期；
- 预约时间前的正常取消、待确认超时取消释放权益；成功预约超过最终确认时间后，取消及反馈必须按REQ-030处理，门诊不得用“无法接诊”绕过保留权益规则。
- 取消2小时提醒。超过最终确认时间24小时创建“过期预约待办”并提醒门诊；达到72小时且无反馈、未决改期或冲突时，将预约主状态改为“完成”，完成来源为“系统超时处理”，关闭原待办，保留权益占用，不核销、不计费。
- 门诊选择“患者未到”则取消预约、关闭原待办，但不释放权益；客户本人提交未到诊申请后，在没有核销/到诊冲突/未决改期的条件下自动恢复权益。
- 系统自动完成与门诊报未到两种情况均在客户首页保留待处理消息。自动完成预约提供“未到诊，申请恢复权益”和“已到诊，完成治疗”；前者取消并恢复权益，后者创建门诊新的“待补核销”任务，仍不收费。详细状态及互斥条件见REQ-030。
- “门诊报告客户未到、客户报告已到诊”等冲突的标准解决流程，以及平台异常处理人的细化权限、处理期限和专项审计要求暂不实现；待出现真实案例后再补充需求，避免预设不符合实际的流程。基础访问控制和操作日志仍必须保留；
- 门诊可针对原预约及仍占用权益补核销，复用扫码与服务完成确认，按REQ-037在实际补核销时锁定费用/分配；不是任意补录。有效期按最终有效预约日期核对，不以实际补核销操作日判断，详见REQ-037；
- 门诊完成服务并扫码核销关联权益后，系统在同一事务中按方案快照扣减固定权益数量、将预约改为“完成”，并形成已生效未结清获客服务费；
- 每次状态变更记录操作者、时间、前后状态和原因；
- 系统自动取消、客户主动取消和门诊以“无法接诊”取消均共用“取消”状态，通过取消原因区分。

**验收标准**：客户提交意向时间后预约进入待确认，门诊预约手机号收到短信且后台出现明显待办；门诊可查看预约手机号并填写不晚于权益到期日的最终日期和时间，确认预约不计费。门诊级处理时限未配置时使用 24 小时，超时预约自动取消并释放权益。客户改期在门诊确认前不改变原预约时间，门诊改期必须确认已与客户协商一致；所有改期均不晚于权益到期日且完整留痕。预约时间后按REQ-030执行24小时待办、72小时系统自动完成但不核销/不释放/不计费；门诊报患者未到取消但不释放，客户本人未到诊申请通过才恢复。MVP不提供冲突裁决操作。扫码核销后预约直接进入完成，按固定数量扣减权益并使对应获客费正式记账；数据库只出现四种业务状态。

### REQ-010 到诊确认与权益核销

**目标**：确保权益只在适用门诊、适用服务和真实到诊场景下使用一次。

**需求清单**：

- 只有当前门诊的授权账号可以核销本门诊可承接的权益；
- 门诊端小程序是现场核销的主要操作入口，应适配扫码、客户出示凭证和必要的人工查询场景；
- 核销前校验权益状态、有效期、适用门诊、关联客户和预约状态；
- 核销操作默认发生在客户到诊且完成约定服务之后；
- 每项已领取或通过不记名卡激活的权益提供固定二维码；客户可出示客户端固定凭证，不记名卡客户也可出示原实体卡二维码，门诊使用门诊端小程序扫码核销；MVP 不使用动态二维码；
- 固定二维码只承载不可猜测的权益标识，不直接编码客户手机号等敏感信息；扫码后必须实时向服务端查询权益当前状态和本门诊适用性，二维码本身不代表核销成功；
- 同一预约的同一次权益消费只能成功核销一次，重复请求返回同一结果而非再次扣减数量；
- 核销记录至少包含权益、客户、门诊、预约、操作账号、核销时间和结果；
- MVP 暂不提供面向客户的错误核销申诉及门诊审核流程；原核销门诊的授权员工可以在门诊端小程序针对本门诊具体核销记录直接执行“撤销错误核销”；
- 撤销前必须展示原核销信息、要求填写原因并二次确认；其他门诊、渠道公司和普通客户不能执行撤销；
- 撤销后系统不得删除或改写原核销记录，而是新增撤销记录、恢复被扣减的权益数量，普通核销撤销恢复原成功预约；系统自动完成后的补核销撤销恢复系统完成且不直接恢复可用权益、不建门诊待办，客户消息及申请按REQ-037处理；
- 撤销操作必须幂等，同一核销只能成功撤销一次；尚未结清的获客服务费同步撤销，已结算账单交易禁止撤销；未结算时撤销并从有效账单中移除，保留审计，不触发已结算后退款；
- 客户和门诊均可查看核销撤销记录和权益恢复结果；平台可以查看并审计，但当前不建设争议仲裁流程。

**验收标准**：无论使用客户端固定凭证还是已激活不记名卡原二维码，预约日期超出权益有效期、未激活、已核销、非本门诊适用、无有效预约或客户不匹配的权益均无法核销；只有原核销门诊的授权员工可以在门诊端小程序直接撤销错误核销。撤销后权益数量准确恢复、预约恢复到核销前状态、费用正确冲销或形成调整，原核销与撤销记录同时保留，重复操作不会重复恢复权益。

### REQ-011 多角色后台工作台与业务查询

**目标**：让各业务主体完成操作并看到各自的数据闭环。

**需求清单**：

- 平台后台：机构、账号、门诊审核、推广产品、异常处理、全局统计和审计；
- 客户资源方后台：统一推广产品销售（两种销售方式、记名批量/单客、采购付款、订单/客户/卡片明细、历史记录）、取消申请/停止剩余申请、待领取/已激活权益、预约和核销；
- 渠道公司后台：签约门诊、审核进度、优惠上线、门诊预约及履约统计；预约仅可查看，不能代门诊确认或核销；
- 门诊后台：本门诊资料、上线优惠、预约处理、到诊、核销和错误核销撤销；
- 门诊后台工作台突出显示待确认预约、客户改期待确认和过期预约待办，支持直接进入沟通、确认、拒绝、改期、取消或核销处理；
- 各后台首页优先展示待处理事项和核心业务数据，不建设空洞展示首页；
- 列表支持必要的日期、状态、机构/门诊和优惠筛选；
- 对于本机构通过 Excel 提供并形成客户资源关系的客户，客户资源方可以查看全部导入及客户明细字段，包括完整手机号；这不授权其查看其他资源方的关系、权益或业务明细；
- 对于仅通过本机构不记名卡激活而建立关系的客户，来源资源方可以查看和导出该客户的全部平台允许字段；这不授权其查看其他资源方关系、权益或履约数据；
- 门诊渠道公司、口腔门诊等其他有权参与方查看一般客户列表时，手机号必须以 `186****1234` 形式脱敏展示；作为例外，当前预约所属门诊中具有预约处理权限的员工可以在预约详情查看本次预约完整手机号；
- 各方均可导出其当前权限范围内的客户资料；客户资源方可导出本方 Excel 关系和不记名卡激活关系客户的完整字段，其他参与方导出的手机号保持脱敏；
- 导出必须经过服务端数据范围校验，生成操作审计并记录导出人、机构、时间、筛选条件、字段和记录数；
- 门诊需要与客户沟通预约时间时，可由具有预约处理权限的员工在具体预约详情查看预约手机号；该访问必须受门诊范围限制并记录审计；
- 首页和列表保留基础待办；平台/资源方客户权益概览与趋势按REQ-029开放，其余经营指标、分析报表和转化看板延期。

**验收标准**：四类后台角色进入系统后，只看到与其职责和数据范围一致的菜单、待办和业务数据；客户资源方能查看和导出本方 Excel 关系及不记名卡激活关系客户的完整字段，但不能读取其他资源方关系或权益；其他参与方的一般页面与导出只能获得脱敏手机号，只有当前预约所属门诊的授权员工可在具体预约详情查看完整预约手机号；任何查看或导出不能突破机构、预约和来源权限。

### REQ-012 消息通知

**目标**：在关键业务节点及时通知客户和业务操作方。

**需求清单**：

- 至少覆盖待领取权益提示、领取成功、不记名卡激活成功/失败、预约提交、预约成功/取消、改期申请/确认/拒绝/超时、预约时间后24小时过期预约待办提醒、72小时自动完成及客户待处理提醒、客户未到诊申请恢复结果、客户已到诊反馈后的补核销待办、到诊提醒和权益即将过期等节点；
- 客户提交新预约后，系统必须向门诊预留的预约联系手机号发送短信；
- 门诊预约确认增加REQ-039跨Tab常驻小窗：新预约只自动更新颜色、文字和数量，窗口展开/收起由前台点击；浮窗失败不影响短信、待办或预约提交。
- 门诊账单从出账日至付款截止日每天最多发送一次付款提醒短信，同时发送给门诊开通时填写的联系人手机号和所属渠道公司的具体负责业务员绑定手机号；逾期首日再发送一次逾期短信，门诊及渠道后台持续显示逾期欠款提示；仅平台实际下线后显示人工下线原因；
- 消息内容不得包含不必要的敏感信息；
- 发送失败可重试并保留状态，不影响核心业务事务完成；
- 所有短信通知使用系统预先配置的模板；业务操作人员不能临时编辑发送内容；
- 平台管理员可以查看、修改、启用或停用短信模板配置，并维护模板标识、使用场景和允许变量；
- 模板修改只影响后续发送，必须记录修改前后内容、操作人和时间；
- 短信费用、发送失败重试、短信服务商对接和模板报备责任均由平台方承担；
- 小程序订阅消息等非短信渠道是否启用可在后续实现阶段决定；
- 用户退订、授权和频率限制必须被尊重。

**验收标准**：关键状态变化可追踪到通知状态；通知失败不会导致预约或核销数据回滚、重复或丢失。

### REQ-013 基础业务来源追踪

**目标**：保证每笔权益、预约、核销和结算明细来源清晰，为基础业务处理和后续扩展提供可信事实；仅REQ-029平台/资源方客户权益分析纳入当前范围，其余经营指标和分析报表延期。

**需求清单**：

- 每次权益、预约和核销都保留不可缺失的投放模式和来源关系，支持追踪 Excel 导入批次/明细或不记名卡批次/单卡、客户资源方、门诊渠道公司和实际履约门诊；
- 同一客户来自多个资源方时，每个业务事件绑定具体来源权益，不得跨来源归因；
- 各角色可查询权限范围内的基础业务明细及为处理待办所必需的简单数量；
- “新客”不作为当前系统概念，不建立新客标记、识别规则或新客统计；
- 除REQ-029明确的两角色客户权益指标与趋势外，经营指标、排行榜和通用分析报表延期；
- 月度结算对账单属于核销结算业务单据，不属于本条延后的经营分析报表。

**验收标准**：任一核销记录均能追溯到推广产品、客户权益、对应的 Excel 导入批次/明细或不记名卡批次/单卡、客户资源方、预约、门诊及其渠道公司。

### REQ-014 安全、隐私与审计

**目标**：保护客户个人信息和机构业务数据，并使关键操作可追溯。

**需求清单**：

- 对手机号、身份信息、权益、预约和到诊数据按敏感个人信息要求保护；
- 当前客户资源方上传模块不要求上传授权证明，不建设面向资源方导入的专项隐私告知确认或可配置数据保留期限功能；
- 上述范围决定不取消系统基础安全、客户小程序通用隐私提示、访问控制、脱敏、导出审计和依法必须履行的义务；
- 采用最小权限、租户隔离、传输加密、存储保护、脱敏展示和安全日志；
- 合同附件、付款凭证、结算资料和不记名卡可激活凭证视为机构商业敏感数据；合同原件只对平台授权人员及合同相关机构的授权人员开放，下载行为必须审计，机构公共合作合同按REQ-034在本机构可查，批量卡凭证只能在当前账号有权访问的订单范围查看；
- 平台客户档案可以跨资源方复用，但客户资源关系、导入数据和来源权益必须按资源方隔离；任何接口不得借共享客户档案形成跨资源方数据穿透；
- 客户资源方可以查看与本机构 Excel 关系或不记名卡激活关系对应的客户全部平台允许字段，但仍必须通过本方来源关系进行服务端校验，不得据此搜索或推断其他资源方数据；
- 登录、批量导入、批次回滚、开卡申请/定价/收款确认/生成/制作寄送/取消/退款登记、单卡下载/激活/作废、权益领取、合同审核/续签/变更、付款凭证审核、在线支付及收款异常、临时下线/恢复、导出、权限变更、门诊审核、方案变更、核销和撤销均纳入审计；
- 日志不得记录验证码、Token、Cookie、完整手机号或完整上传文件内容；
- 对短信验证码、登录、账号绑定、权益领取、不记名卡扫码与激活、预约和核销设置防刷、限流和异常检测；
- 客户个人信息查询、更正和注销等平台通用能力在后续范围评审中确定；
- 未经额外授权，不得将客户数据用于跨机构营销、出售、通用模型训练或与本业务无关的画像。
- 平台运营、平台财务、门诊管理员、门诊前台等更细角色权限矩阵暂不在本轮讨论；开发阶段仍必须执行当前文档已经明确的最小机构隔离和操作权限，细化矩阵在功能完成后的专项评审中确定。

**验收标准**：通过共享客户跨资源方隔离、角色越权、跨机构访问、错误客户绑定、重复导入入账、重复核销、日志泄露和接口防刷专项验证。

### REQ-015 客户端小程序与门诊端小程序

**目标**：客户端与门诊端使用两个独立微信小程序，共享同一服务端业务事实和权限规则；普通客户在客户端使用权益，获授权门诊员工在门诊端完成现场核销和本门诊业务处理。

**需求清单**：

- 客户端小程序和门诊端小程序具有独立入口、独立界面和独立登录态，不提供两个工作区之间的切换入口；
- 普通客户和门诊员工均优先通过各自小程序取得微信授权的默认绑定手机号注册或登录；
- 同一手机号可以同时对应平台客户身份和门诊员工身份，并分别登录两个小程序；两种身份不合并，数据和权限不得串用；
- 门诊员工不能在门诊端小程序自行注册成员工。门诊管理员必须先在后台创建员工记录，填写姓名、手机号、所属门诊、角色和权限；
- 员工首次进入门诊端小程序时，系统用微信授权手机号匹配有效员工记录，确认后建立小程序账号与员工身份绑定；未预先开通、手机号不一致或已停用时不能进入门诊端；
- 支持门诊管理员开通、修改、停用员工，并分别控制“处理预约”“核销权益”和“查看业务数据”等权限；
- 客户身份与员工身份的数据和权限独立；同一自然人在客户端只能查看本人权益，在门诊端只能处理所属门诊业务；
- 员工如被授权到多个门诊，进入门诊端后必须先选择当前门诊，所有后续查询和操作均带入该门诊范围；
- 首页优先展示待确认预约、今日成功预约、今日已完成预约和异常待办；不设置独立到店状态；
- 支持扫描客户已领取或已激活权益的客户端固定二维码，也支持扫描已激活不记名卡原二维码，并提供受限的人工查询兜底；
- 核销前清晰展示客户核验信息、推广产品、来源说明、有效期、可用数量、适用门诊、预约及本次消耗数量；
- 核销前必须由操作人确认，成功后显示明确结果，连续点击或网络重试不得重复扣减权益；
- 核销失败时展示可操作的原因，例如已核销、已过期、非本门诊适用、数量不足或预约状态不允许；
- 具有撤销权限的员工可以在门诊端小程序查看本门诊核销记录，并对错误记录填写原因、二次确认后执行撤销；
- 支持查看本门诊的预约与核销业务明细，并可按日期、推广产品和状态进行必要筛选；具有预约处理权限的员工可在具体预约中查看预约手机号；不提供经营指标和分析报表；
- 移动端数据只限本门诊，不展示其他门诊、渠道公司整体或资源方非必要数据；
- 客户手机号等敏感信息默认脱敏，只有完成现场服务所必需的字段可以展示；
- 员工停用或离职后应立即失去查询和核销权限；门诊暂停、合同到期或退出后，员工只保留完成状态变化前已有预约所需的受限查询、确认、改期和核销权限，不得承接新预约；
- 登录、查询、扫码、核销成功/失败和员工权限变更均保留审计记录；
- 网络异常时不得离线核销或先成功后补传，避免权益被多门诊重复使用；可提示用户重试或转人工处置。

**验收标准**：普通客户通过客户端小程序完成客户业务；预先开通的门诊员工通过独立门诊端小程序完成门诊业务。手机号同时具备两种身份时可以分别登录两个小程序且数据不混淆，不出现工作区切换。获授权员工可仅使用手机完成“查看预约—核验权益—确认核销—撤销错误核销—查看结果”闭环；未开通员工、无核销权限、非本门诊、已停用账号和重复请求均无法造成权益扣减或恢复。

### REQ-016 门诊周/月账单、收款与三方结算

**目标**：取消门诊授信，以实际核销计费、按合同周结/月结出账，支持付款凭证审核与微信扫码在线支付两条收款路径。

**已确认边界**：不预存、不授信，不设置已用/可用额度、风险敞口、调额审批或额度恢复。在线收款本次仅用于门诊获客服务费账单；不记名卡购卡仍线下付款。三方收益分配仍线下完成，不扩展自动代扣、储值、支付分账或发票。

**计费与出账**：

- 预约提交只占用客户权益，不计费、不计算待履约风险金额；确认保存固定单次核销数量，费用及分配仅在核销时锁定。取消不产生费用，过期预约的权益释放按REQ-030。
- 核销成功在同一事务中扣权益、完成预约、生成一笔未结清获客服务费及来源资源方/渠道方/平台方收益明细，重复核销不重复记账。
- 每家门诊独立按三方合同选择周结/月结：周结周一至周日，次周一出上周账；月结每月1日出上月账。每笔核销费用只进入一个有效账单，重试不重复出账，周期变更不追溯重出历史账单。
- 各合作方付款期限统一周结出账后3个自然日、月结出账后5个自然日，出账次日起算，不沿用旧工作日口径。已出账截止时间不因合同改期而追溯修改。
- 账单包含门诊、三方合同版本、账期、核销/调整明细、应付、已确认收款、未付、截止时间、账单状态及付款记录；不再显示授信数值。

**线下付款凭证**：

- 门诊在本门诊账单详情上传付款凭证，填写金额、付款时间、付款方及必要的银行交易参考号/说明；可多附件，提交进入付款待审核。
- 平台管理员在收款审核页查看账单、全部凭证、已登记到账和审核历史，核实实际收款后通过，或填写原因退回；上传截图本身不代表到账，门诊和渠道不能确认收款。
- 退回后可修正重新提交，保留每次提交附件和审核记录；同笔银行款项不得重复登记或跨账单重复核销。
- 沿用“不支持部分冲销”：不足额线下到账允许登记，但账单全额到账前不结清；保留累计收款和剩余应付。付款待审核不免除已逾期提示。

**微信扫码在线支付**：

- 门诊在账单详情选择“微信扫码支付”，系统按当前账单剩余应付生成关联账单和收款主体的支付订单及支付二维码；不使用个人静态收款码代替订单支付，不允许自行输入任意账单金额。
- 展示账期、门诊、收款方、应付金额、二维码有效性及支付结果。二维码失效可刷新；支付取消、失败或结果未知时账单仍未结清，不因“我已支付”、截图或前端跳转判定成功。
- 服务端验证支付通知及主动查单的可信结果，核验订单、收款商户、金额和币种后登记收款；重复通知、刷新及重试只能结清一次。成功在线款不再要求管理员重复审核；支付成功与商户资金结算入银行分开记录。
- 原型仅模拟；真实接入前确认平台合同收款主体、商户资质及开通产品。后台桌面扫码；门诊小程序管理员在账单详情发起微信支付，不能要求同一手机扫描自己的屏幕，见REQ-036。
- 同一账单同时只保留一个有效在线支付尝试；线下凭证待审核时暂停新在线订单，在线结果未决时先查单/关单确认再允许切换线下路径。不得只依靠按钮禁用防止重复收款。
- 线上线下仍可能发生交叉到账：所有真实资金记录均保留，超额或重复款进入待处理异常，不再次冲销、不静默丢弃、不自动当作下期余额。结算中发生核销撤销/账单金额变化时先协调未决支付，校验版本及金额，不能用旧金额误结清。
- 微信支付本期先完成代码及可执行模拟测试，主体、商户号、开通能力、密钥及手续费在真实启用前补齐并完成真实联调；当前不擅自增加自动退款。重复/超额款完整处置按REQ-037延期，基础防重、真实流水保留及异常提示仍必须实现，不把这些外部准备阻塞代码开发。

**逾期、催收与收益**：

- 门诊支付逾期不自动下线或退出搜索，系统显示逾期与催收提醒，由平台人工决定上下线并记录原因。付款到账不自动撤销平台人工下线；资质、合同、产品等独立限制仍有效。
- 出账日至截止日每天最多一次短信通知门诊联系人和渠道负责业务员；逾期首日一次逾期短信，门诊/渠道工作台持续显示欠款与原因。
- 渠道查看所管门诊账单、欠款、付款进度并负责催收，不承担担保责任；不代门诊提交付款、支付或确认到账。
- 存量待确认/成功预约不因欠款被批量取消，保留必要履约权限。
- 三方收益保留核销及原合同分配快照；合作方每月归集全部历史中门诊已结清且本方尚未入单的交易，生成月度对账单及逐笔明细；资源方/渠道确认本方单据后，平台上传付款凭证后待合作方确认收款，确认后完成；平台不另建自身收益结算单。按REQ-025支持异议及Excel下载，不得查看或修改他方金额；渠道归属变更不改已核销业绩；变更后新核销归核销时渠道（REQ-042）。
- 错误核销未结清时冲销费用并相应修订账单版本和收益明细；已完成结算账单的交易禁止撤销核销；未完成结算可撤销并移除有效交易、重算账单，保留原核销和账单版本。支付未决先核实，按REQ-037防止并发已结算仍撤销。零负金额不生成付款请求。
- 出账、附件、收款审核、支付下单/查单/回调、关单、异常、冲销及结账均留审计；签名密钥及敏感支付信息不得写入前端或日志。

**验收标准**：无授信字段/调额菜单/风险拦截；预约不产生费用，核销一次计费一次。周/月出账和付款期限准确；凭证上传不结清，审核退回可重提，全额确认才结清。在线真实成功才入账，二维码过期、伪通知、金额不符、重复通知、回调丢失、并发线下审核及撤销均不能重复/错误结清。渠道无收款审核权。原有三方月度对账及历史调整保留。

支付技术事实参考微信支付官方[支付通知](https://pay.wechatpay.cn/doc/v3/merchant/4012164515)中的验签、金额核验和重复通知处理要求，以及官方[回调与查单说明](https://pay.wechatpay.cn/doc/v3/partner/4012085875)；2026-09-08核验。页面涉及合单/服务商的示例仅用于核验通用回调机制，不代表本项目采用该商户模式，具体普通商户接入见后续ADR。

### REQ-017 客户资源方权益投放与不记名卡

**目标**：支持客户资源方通过不记名卡和 Excel 名单两种当前模式投放权益，同时为未来的单客户小程序购买赠送保留清晰边界。

**当前范围**：

- 模式一“不记名卡批次”：资源方购买一批未绑定客户的权益卡，客户首次扫码激活后预约并到诊核销；
- 模式二“记名非实体卡”：资源方通过Excel批量客户或后台单个客户录入购买，平台审核后匹配客户并分配待领取权益；
- 资源方小程序的单客户购买赠送继续延期；后台单客采购本轮纳入，但必须走统一销售订单，不允许直接发放。

**不记名卡需求清单**：

- 资源方在有效合同授权内选择推广产品和来源展示名，填写数量、每卡份数和单卡采购价（默认0元）提交订单；不能自行创建或修改推广产品、来源展示名。
- 订单提交即保存单价和总额快照；非零价必须平台确认全额到账后才能审核，零元直接审核。平台审核价格、授权及有效期（默认180天，可修改），通过时完成开卡；
- 开卡订单至少记录申请/订单编号、来源资源方、来源展示名、推广产品、卡单价、卡片数量、订单总金额、每卡权益数量、申请/审核时间、有效期天数、线下收款状态、线上确认人、实体卡制作/寄送状态和操作记录；
- 不记名卡购买是资源方向平台购买卡片的系统内业务操作；非零订单实际付款在线下完成，平台管理员确认全额收款并审核通过后才能生成卡片，零元订单不伪造收款；系统不直接收款或处理发票，也不得因重复提交或任务重试超量生成；
- 平台完成开卡后在线下制作实体卡并邮寄给购买方，系统记录制作完成时间、寄送时间、收件信息和必要物流凭据；
- 每张卡只有一个来源资源方、一个推广产品和一个唯一不可猜测标识；二维码不得直接包含客户信息、资源方内部资料或连续可枚举卡号，服务端应只保存满足校验与追踪需要的数据；
- 卡片生成、批量下载、打印文件下载、作废申请和作废处理属于高风险操作，必须进行服务端权限校验、二次确认和审计；导出文件不得包含已激活客户的明文个人信息；
- 激活前卡片不属于任何客户，合法持有人可以转交；首次成功激活后立即绑定当前客户档案并不可转让，同一卡在并发请求下只能成功激活一次；
- 激活同时建立或复用“当前客户—来源资源方”关系，生成可使用权益并保存卡批次、卡标识、来源展示名和方案规则快照；不经过 Excel 手机号/姓名匹配，也不进入待领取状态；
- 资源方可以对开卡订单申请取消；未生成卡片时可进入平台取消审核，已生成卡片时系统必须检查订单批次全部卡片均未激活，任一卡已激活则整单不能取消；MVP 不支持部分取消；
- 平台确认取消已生成订单时作废该订单全部未激活卡片；已经线下付款的订单由平台线下完成退款，并在系统登记退款金额、日期、凭据和操作人，系统不直接执行退款；
- 资源方申请撤销卡批次时，只能作废尚未激活的卡片；已激活或已核销卡片及其客户权益不得随批次撤销而失效，系统保留批次、作废范围和审计记录；
- 未激活卡可以按授权作废；已激活卡不得转让、换绑或重新激活；
- 发生卡片丢失、二维码泄露、冒领或归属争议时，由平台管理员冻结单卡及其关联权益，冻结期间不得激活、预约或核销；平台人工核查后只能执行解冻继续使用或受控终止，并记录依据、操作人和审计，不允许普通业务方直接改绑；
- 已激活卡的原卡二维码可以作为固定权益凭证，但门诊扫码必须实时校验当前客户、关联预约、权益状态、有效期和门诊适用性；客户端也应提供同一权益的固定凭证，避免必须依赖实体卡保存；
- 未登录用户、非门诊人员或其他客户扫描已激活卡时，不得获得原持有人的姓名、手机号、权益余额、预约或核销信息；
- 不记名卡不设置激活截止日期；客户激活时按开卡订单确定的有效期天数生成权益并从激活成功时间起算，默认 180 天；
- 资源方可以查看本机构开卡订单、卡批次、激活数量、未激活数量、作废数量、客户全部平台允许字段及履约结果，但不能查看其他资源方与同一客户的关系和权益；
- Excel 名单导入继续遵循 REQ-004 的手机号/姓名匹配、待领取、跨资源方隔离、同批幂等和整批回滚规则；两种模式的权益在客户账户中均保留独立来源凭证，不得合并成无法追踪来源的余额。

**验收标准**：资源方选择推广产品、来源及100张数量，填写采购价提交订单；零元直接审核，非零须先全额确认到账，再审核开卡。通过后准确生成100个唯一卡号、登记不重叠号段及独立随机激活凭证，并记录制作寄送。卡片不设置激活截止日期，客户激活后从激活时间开始计算到期日；任一卡在并发扫描和重试下只产生一笔客户权益。订单全部卡片未激活时可整单取消、作废并登记线下退款，任一卡已激活时拒绝取消；已激活卡不得转让，争议卡可冻结；资源方可查看本方关联客户完整字段但不能穿透其他来源；Excel 权益从领取时间起算有效期；后台单客采用同一采购审核流程，小程序单客购买赠送入口仍不提供。

### REQ-018 合同管理与业务权限控制

**目标**：以平台合作合同和门诊三方合同控制业务权限，区分平台配置权、渠道签约操作权和门诊履约权。

**合同类型**：

1. 平台—客户资源方合作合同：一份主合同、多方案和历史版本，由平台管理，资源方只读。
2. 平台—门诊渠道公司合作合同：同一时点只有一个生效合同，可含多个方案及本渠道分配规则，由平台管理，渠道只读。
3. 平台—渠道公司—门诊三方服务及结算合同：渠道负责组织签订、录入、提交和续签，平台审核；同一门诊同一时点只允许一个有效版本。

- 三方合同替代后续业务中的渠道—门诊及平台—门诊双边合同；历史记录保留原签约主体，不通过改名伪造已签三方合同，补签或迁移必须有签署依据。
- 各类合同记录编号、主体、期限、状态、业务范围、全部附件、版本关系、操作人和审核记录；续签/变更不覆盖历史。结算责任在三方合同明确，渠道加入合同不自动承担担保责任。
- 渠道在门诊管理中处理门诊三方合同；不能编辑自身平台合同、平台授予的方案或任何收益分配值，也不能审核自己提交的合同。
- 平台在合作方合同中配置方案授权及比例/金额；三方门诊合同引用当前渠道授权范围，避免复制为门诊另一套独立上游费率。
- 服务端统一校验合同主体、当前门诊归属、状态、期限和方案范围。门诊三方合同只能引用本门诊及其当前渠道，跨渠道篡改字段/附件访问必须阻断。
- 资源方无有效平台合同时不能新建Excel或开卡申请；渠道无有效平台合同时不能新增门诊、上线优惠或扩大授权。允许查看历史、必要的账单催收及存量履约。
- 合同到期后允许渠道继续维护并提交必要续签资料，但不因此开放新预约或优惠上线；三方合同系统内仅平台审核，审核时限2个工作日，详见REQ-042。
- 门诊没有有效三方合同或有效渠道方案授权时不能产生新预约；旧预约、权益、核销、账单和历史查询按既有规则保留。
- 所有门诊审核页面可查看本次全部照片/附件、旧版本和本次变更；合同审核不等于授予其他无关机构附件访问权。
- 平台只在其权限范围审核合同/确认线下收款；细化岗位矩阵延期不取消上述明确责任。发票及电子签章接入不在本次范围。

**验收标准**：三类合同分别覆盖未生效、有效、到期、终止和续签待审核；阻断有效期重叠。渠道可签订/续签本方门诊合同但不能自行审核，不可修改自身平台合同。所有附件可读且隔离，旧双边历史不改主体。失效合同阻止新增业务但不删除存量事实。

### REQ-019 独立角色后台原型与 Arco Design 设计基线

**目标**：先交付平台、客户资源方、门诊渠道公司和门诊四组独立后台原型，作为后续前端开发评审依据。

- 每个角色单独入口、页面组和业务数据；不设置跨角色切换器，不把角色页面拼接到同一个工作台。
- 保险、银行、经纪代理属于客户资源方组，保留固定机构类型，不提前细分尚未确认的岗位权限。
- 原型和正式 Web 开发统一遵循 `docs/design-requirements.md`；使用 Arco 官方组件、主题与交互规范，项目约定和官方要求明确区分。
- 覆盖各组工作台、列表、筛选、详情、主要操作表单和状态反馈；展示权限内数据及关键操作限制。
- 本轮为后台原型，不扩展小程序页面；样例数据独立保存，文件选择不上传，收款和短信只展示流程，不执行真实业务。
- 原型可在业务基线评审期间制作，不代表 TASK-007 的正式 MVP 冻结已经完成。

**验收标准**：四组可独立打开，菜单和操作各自对应角色；无跨角色业务数据加载；主要操作、表单校验、搜索、详情和演示状态可交互；Arco 基础组件及视觉规则一致；完整页面清单和原型限制记录在 `docs/prototype-review.md`。

### REQ-020 合同级权益授权与获客费分配

**目标与范围**：平台按合作方合同配置可用推广产品及本方分配规则；客户资源方、渠道公司和门诊只能在授权范围内开展新业务。关联 REQ-018；本节取代原方案级统一三方分配配置口径，推广产品仍定义单次核销数量、获客费和使用条件。

- 平台—资源方、平台—渠道公司合同均可添加多项推广产品；每项记录方案、按比例/按金额、分配值、启停状态、版本和变更原因。比例基数为该方案单次获客费，金额单位为元/次核销，与购卡单价无关。同一合同同一方案不可重复有效授权。
- 合同未生效、到期、终止或方案授权停用时不得开展该方案的新业务；授权有效期沿用合同期限。仅创建或启用全局推广产品不授予任何合作方使用权。
- 资源方只能选择本方有效合同授权且已启用的推广产品下单；一单一个产品，提交和审核时均复核授权，不能借Excel或单客录入绕过限制。
- 渠道及其负责门诊只能为当前渠道有效平台合同授权的方案上线优惠；同时满足门诊三方合同有效、资质/服务状态及账单限制才可承接新预约。门诊不单独取得渠道方分配比例，不能扩大上游授权。
- 平台在机构管理的合作合同内提供“推广产品配置”入口，支持新增、编辑、停用、重新启用和计算预览；合作方只能查看本方规则，门诊只看方案授权及获客费，不展示其他方分配合同。
- 平台按资源方配置来源展示名：新增、编辑、启用、停用，支持从机构直接进入；资源方仅选择本机构已启用名称。展示名不改变实际来源机构、合同主体或资金归属；变更仅影响后续投放，历史名称快照保留。
- 不追溯修改历史权益、已确认预约、核销和账单。授权撤销不作废已发权益或已开卡；存量领取/激活及已有预约继续按历史承诺处理。新预约仍须找到当前授权可承接门诊，不能绕过渠道授权。
- 服务端必须统一校验合同主体、类型、有效期、方案、当前门诊归属及操作权限，并在关键提交时复核；原型前端规则仅供交互评审。

**已确认（0.29）**：平台收益按获客费减去资源方及渠道方收益的余额计算；允许两方分别使用比例和固定金额。以60元为例，资源方20%=12元、渠道固定18元，平台30元。比例0–100%，金额非负且精确到分；每方四舍五入到分，平台取余额以保持总额一致。可履约组合两方金额合计不得超过获客费；同主体同方案在重叠合同有效期内不允许多条有效规则，避免优先级歧义。核销前费用/分配不锁定；核销时按适用规则确定并保存快照，重试沿用同次核销结果，已核销后不得随调价重算（REQ-037）。

**验收标准**：同方案可在不同合作方合同配置不同费率，支持比例/金额混合；60元示例得到12/18/30。无授权不可购卡、导入入账或上线门诊优惠；停用后不能新增，存量履约保留。重复授权、超额分配、无效合同及跨资源方展示名均阻断。资源方不得查看别家名称列表；门诊不得修改合同费率。所有新增/修改/启停记录操作者、时间、原因、前后版本及关联合同方案。来源名调整不得改写历史投放。

### REQ-021 所有后台列表按记录状态分 Tab

**范围**：平台、客户资源方、渠道及门诊全部后台列表页，原型和正式开发共同遵循。不改变业务状态机、数据权限或原有操作责任。

- 每个列表使用 Arco 状态 Tab，默认“全部”，其后为该业务的记录状态；移除重复的状态下拉框。单一状态列表也使用同一结构，不将客户身份、合同类型等非状态字段混为状态页签。
- 页签显示状态名称及记录数；计数基于本角色权限、当前合同/机构范围和关键词过滤后的全部记录，不受当前页码或已选状态影响。
- 状态顺序固定，零记录的既定状态仍显示；切换页签保留关键词和合同范围，回到第一页。重置查询恢复“全部”和空关键词，但不解除合同/机构范围；“查看全部”才解除该范围。
- 记录状态变更后自动更新数量和列表；当前页签不跳转，移出的记录不再显示，可从目标状态页签查看。详情关闭不丢失筛选；导出仅包含当前状态与查询条件匹配的记录。
- 页签较多或窄屏时使用官方横向滚动，保留完整状态文案和可访问名称；不把多状态合并为含义不明的“其他”。详情中的试算表不属于独立业务列表，不为其虚构状态。

**验收标准**：四组全部业务列表均有“全部”及状态Tab，无状态下拉；验证状态/关键词/合同范围交集、计数、零记录、分页重置、状态变更、导出范围以及窄屏溢出，原有角色限制及关键操作不退化。正式版本由服务端按相同权限范围计算各状态数量。

### REQ-022 合作合同与可用方案合并展示（0.18修订）

**目标**：资源方和渠道自身合同均为只读信息，不再拆成合同列表、授权方案两个一级菜单。

- 资源方“合作合同与推广产品”：上部直接展示唯一主合同摘要、期限、状态及附件；下部同页展示全部合同方案、使用条件、单次获客费、本方分配模式/值和有效性。历史版本可展开查看，方案不另建平行主合同。
- 渠道“平台合作与推广产品”：同一页面展示当前唯一生效平台合同、合作范围、完整可见附件及本渠道全部授权方案/本方分配；保留历史和待生效版本查看，无生效合同时明确空状态及限制原因。
- 两方均只读，不提供新建/编辑平台合同、签订/续签提交、添加推广产品、修改费率或授权启停按钮；以上配置由平台管理员完成。
- 表中的方案是合同授权状态，不是某家门诊上下线状态。资源方导入/开卡仍在各自业务入口；渠道给具体门诊上线方案须进入门诊管理。
- 单合同摘要不是列表，不强造只有一条的状态列表；嵌入方案列表和历史版本列表仍按REQ-021使用全部及记录状态Tab，合同期限和方案授权有效性清晰区分。
- 渠道原“平台与门诊合同”和“门诊优惠”入口整合进“门诊管理 → 具体门诊 → 合同与续签/推广产品”；原REQ-022的双列表布局被本条替代，不再作为当前设计要求。
- 返回门诊列表保留筛选/分页/滚动位置；同一详情内切换资料、合同、优惠时保持门诊上下文，明确不同区块的操作权限。详情分区不取代其内记录列表的状态Tab。

**验收标准**：资源方和渠道各用一个只读页面看清自身平台合同和全部授权方案；不重复一级菜单，不出现平台配置按钮。渠道从任一门诊记录直接进入该门诊的合同/续签/方案，不重复选择机构，不串门诊。合同多方案、单有效渠道合同、数据隔离和列表状态Tab规则均保留。

### REQ-023 两个独立小程序交互原型

**目标**：交付客户端、门诊端两个独立移动原型，覆盖现有REQ-005、008、009、010及账单结算的主要入口和异常路径。不改变已确认业务规则，不扩展资源方小程序单客户购卡、客户核销争议审批或经营报表；门诊账单支付按REQ-016/024后续同步。

- 客户端：手机号授权登录、待领取提示、权益列表/详情、领取、不记名卡激活、固定凭证、附近门诊/手动地区、预约提交、四状态预约列表、详情/取消/改期/到诊反馈、通知及个人资料（手机号不可改）。不同来源权益独立展示，领取和激活后按180天示例起算有效期。
- 门诊端：员工预开通与绑定说明、手机号登录及未开通/停用阻断、工作台、四状态预约列表/详情、人工确认时间、客户改期审核、门诊协商后改期、无法接诊取消、履约反馈待办、扫码核验/服务完成确认/核销结果、核销明细及错误核销撤销、账单及收款进度、消息与本门诊资料。
- 原型使用人工构造数据，两个角色和原有后台的数据、登录态互不共享。测试评审日期固定为2026-09-07；用演示凭证输入代替真实相机扫码，用页面反馈代替真实短信。固定凭证不含手机号，明确不可用于真实核销。
- 模拟操作须校验可用数量、重复领取/激活/核销/撤销、到期、预约归属/状态、改期日期和协商确认；提交预约仅占用权益，不计费；核销才计费；旧0.28原型撤销逻辑为历史行为，0.29应按REQ-037区分特殊撤销和人工退款，不假冒退款或到账。
- 身份授权和正常页面内容区分，拒绝授权可以返回；门诊员工身份由后台预留手机号确认，不让普通客户在门诊端自动注册员工。协议/隐私页面本次只说明演示范围，不作为上线法律文书。

**验收标准**：两端独立打开并能完成主要模拟闭环；375/390/430px可读且底部导航不遮挡操作，业务列表按状态Tab；异常输入有可恢复提示，刷新保存演示记录；明确真实微信授权、扫码解码、GPS、短信、服务端校验/事务、定时任务及跨端同步未接入。

**范围确认与后续接入条件（0.32更新）**：

1. 已确认逾期不自动下线，由平台人工操作；其余资质、合同、产品和人工下线限制保留。

6. 合同结算周期变更立即生效、不追溯已出账单；保留原签订/变更审核权限。未出账存量按新账期归集，见REQ-037，不假定变更当天自动出单。

**验收用例**：

### REQ-028 推广产品销售统一订单

**目标**：资源方将原Excel批次、开卡订单和不记名卡批次整合为“推广产品销售”；平台在对应销售管理内核实采购收款、审核开卡、查看客户/卡片/号段/物流及退款。保留各角色独立入口，客户权益来源和既有履约/分账规则不改变。REQ-004/017及旧流程中冲突的入口、定价责任、付款审核顺序以本条为准。

**销售方式与数量**：

- 不记名实体卡：不上传Excel、不录入或预绑定客户，仅填写开卡张数，再选择获授权推广产品、来源展示名、每卡权益份数及采购单价。平台审核通过后按数量自动分配号段并生成卡片，保留制作/寄送记录；客户首次扫码激活时绑定。
- 记名非实体卡：先选择批量客户或单个客户。批量上传Excel客户编号/姓名/手机号/该客户开卡数量，单个客户用表单录入相同字段。每单统一选择一个获授权推广产品、来源展示名及每卡权益份数；不同产品拆订单（最小范围默认）。明细数量汇总为销售张数，禁止再填不同总数覆盖。
- 区分客户数、卡片张数和每卡权益份数；客户权益份数=客户卡片张数×每卡份数。批量文件各客户数量可不同。单客户可购买多张，不称为只能购买一张的“单卡”。
- 两种方式单卡采购价均由资源方填写，默认0元、不可负、精确到分；它是资源方向平台的采购价，不是患者付款价，也不是门诊获客服务费或合作方收益分配价。订单总价=卡片张数×采购单价，提交后冻结数量/价格/产品和客户清单。平台审核允许或拒绝本次价格，不静默改价，需改价重新下单。

**订单流程**：

- 零元：提交→待审核→平台审核通过并开卡→已开卡；无需假造付款凭证或已到账记录。
- 收费：提交→待付款→资源方上传凭证→付款待确认→平台确认全额实际到账→待审核→平台审核通过并开卡。凭证上传不等于到账，付款方不能自确认；单价非零但未全额确认不能审核开卡。原型沿用线下付款，不顺带接入新的在线支付。
- 同页详情显示付款记录、全部凭证、审核意见与开卡结果，平台确认收款和审核开卡是两个事实。凭证退回回到待付款并保存原件；已付款审核不通过保留待退款标记，由平台登记线下退款；不自动退款、不转余额。
- 平台审核时复核机构合同、产品授权和来源展示名、采购价格、客户明细匹配及有效期（默认180天，可审核修改）。有错误明细整单不得通过，先修正后另单提交；暂不实现部分开卡和部分退款。
- 客户匹配仍按规范化手机号及姓名一致性，手机号命中姓名不符为异常；同一客户跨资源方复用平台档案并保留独立来源关系。未注册客户创建未绑定档案。校验预览不创建档案，只有审核通过才生成记名待领取权益。沿用客户主动领取及领取日起算有效期；实体卡从激活日起算，不设激活截止日期。
- 取消/停止不删原单：未开卡可申请取消；开卡后实体卡全未激活或记名权益全未领取时可整单取消，平台审核后作废。任一已领取/激活禁止整单取消，记名订单仍可由资源方申请、平台审核停止剩余未领取部分；保留原客户档案与其他来源权益。已收款订单取消进入待退款，由平台记录实际线下退款。
- 成功订单、付款、审核、客户分配及号段生成均考虑重复提交/重试幂等；失败不能产生半批卡或半批客户权益。

**卡号及号段**：

- 实体卡卡号由系统自动分配，不由资源方填写；每单记录批次、起止号、张数、生成时间及关联订单。全平台卡号唯一、号段不重叠；系统原子分配，订单重试复用原号段，取消/作废号段不回收使用。

- 资源方/平台各自销售列表按订单状态Tab；新建向导按销售方式只显示所需字段。订单详情包含客户清单/卡片/号段/采购付款/审核/后续处理。平台负责到账确认和审核，资源方仅下单、付款凭证、查询与取消/停止申请。
- 旧入口不再新建业务；原始Excel、订单、卡批次在统一页面的历史区保留只读查询，不伪造其价格、客户、付款事实或补发权益。旧链接跳转统一入口，缓存升级前备份。历史异常处置需依据原记录，不通过新版订单重复开卡。
- 工作台相关待办合并为销售处理，直接打开具体订单并办理。客户/门诊小程序领取、激活、履约入口不合并，不增加小程序单客购买流程。
- 原型可使用无敏感信息的模板/演示Excel检查列及客户匹配，不代表生产Excel解析、安全扫描、跨机构共享、跨角色支付状态或自动发放已实现。

**验收**：两种方式/两种客户录入、数量及总价、零元免付款、收费到账前审核阻断、凭证退回/收款/审核、授权/手机号姓名错误阻断、未绑定客户、号段不重叠与重复开卡阻断、原价冻结、取消/部分已领取停止/退款记录、状态Tab、旧缓存/旧链接以及待办页内处理。财务结算REQ-025保持独立，采购付款不触发门诊已结清或合作方收益。

### REQ-029 平台与资源方客户权益概览

**目标与范围**：资源方“客户与权益”升级为“客户与权益概览”，平台新增独立同名页。提供客户/产品投放及转化汇总、指标趋势、明细查询和下载；不是开卡、发放、修改权益或财务记账入口。只开放这两个角色的本项分析，其他角色和经营报表继续延期。

**数据范围**：
- 资源方只读取本方销售、客户关系及来源权益；不能获取其他资源方名单、指标或筛选选项。平台可选全部资源方或一家资源方，不以角色切换器拼接页面。
- 支持推广产品、销售方式和开卡批次日期范围；默认近期开卡批次，截至查询时点观察其后续转化。平台客户数使用平台客户ID全局去重，不能直接相加资源方人数；同理产品客户数不能直接相加为顶部人数。数据按稳定产品编号关联，后台显示内部名称。
- 同一筛选批次集合用于顶部、产品表、趋势与明细。只有平台审核成功的开卡事实纳入采购；待付款、付款待确认、待审核、拒绝订单不算采购成功。

**指标定义**：
| 指标 | 单位/定义 |
| --- | --- |
| 客户总数 | 人；当前批次范围内建立本方关系的客户去重，记名开卡后含未注册客户；不记名激活绑定前不计人，关系建立后不因卡作废删除客户 |
| 有效采购数量 | 张；截至观察时点成功开卡数扣除已取消/作废/停止的卡，另列退出张数；零元审核开卡同样纳入 |
| 已激活数量 | 张；有效卡中不记名激活或记名领取成功的卡，已用完/过期不抹去其曾激活事实，冻结不等于作废 |
| 累计有效预约 | 次；截至观察时点处于待确认、成功、完成的预约；取消排除，改期不新增次数 |
| 有效核销 | 次；实际核销记录，扣除已撤销记录，另显示有效消耗权益份数，不以门诊是否回款判断 |
| 激活/预约/核销客户数 | 人；对应上述各阶段的去重客户，同一人多卡、多预约不重复算人 |
| 卡片激活率 | 有效卡已激活张数÷有效采购张数 |
| 客户预约率 | 有有效预约客户数÷已激活客户数 |
| 客户核销率 | 有有效核销客户数÷有有效预约客户数 |

所有比例使用未四舍五入的分子/分母，显示一位小数，分母为0显示“—”。客户激活率不混用：不记名卡不知道发放客户数，因此统一使用卡片激活率。三阶段分子均须来自同一范围且满足前阶段，异常关联记录应提示数据质量问题，不强行裁剪百分比。

**趋势与明细交互**：
- 点击顶部任一指标或产品行指标，打开趋势抽屉，保留当前筛选，并显示当前对象、口径、单位和观察截止时间。
- 支持按天/按周/按月，周一至周日为一周，自然月；Asia/Shanghai。数量可看“期末累计”和“本期净变化”，后者为相邻期末差值，可为负，不称为单纯新增。人数按每个时点重新去重，不能加总日去重人数。比率只展示各期末比率并列分子/分母，不能平均日比率得到周/月比率。
- 趋势追踪同一开卡批次集合，各点仅读取该时点之前发生的开卡、绑定、激活、预约状态与核销/撤销事实；取消/撤销按实际变更时间影响此后点，不用当前状态覆盖过去。无数据时数量0；零分母率为空点，不画成0%。
- 产品汇总按产品状态Tab；明细按卡、预约、核销等实际状态Tab。支持搜索、分页和当前筛选全量Excel导出，不只导出当前页；比例明细区分分子和分母，人数明细必须去重，点击可追溯来源卡/订单。
- 旧客户演示记录只读保留在历史区，不凭汇总数补造开卡或激活日期。无法获得关联或时间依据的历史数据明确标记未纳入分析及原因。
- 原型使用清楚标记的独立分析样例演示跨月转化、多来源同客户、取消、核销撤销和多卡；同角色新审核销售单的可追溯卡片可进入概览。跨角色共享、真实历史回填、定时聚合、正式服务端权限/事件账本不是已完成能力。

**验收标准**：两个独立入口；资源方不可越权；平台全局去重及资源方筛选；多产品、数量单位、零分母、两种激活口径、三种预约状态、取消与核销撤销、按事件时点回放、周/月边界、同批跨月转化；所有指标可点击查看日/周/月曲线和明细；图表/表格/Excel数据一致，全筛选导出；采购审批前不增长、审批后同角色可观察增长，原有财务及小程序不受影响。

**待确认/生产前细化**：默认展示范围暂定近期开卡批次，使用净变化而非毛新增；大规模历史数据覆盖起点、聚合刷新频率及最终字段权限由正式实施评审。本轮不新增短信、营销触达或客户资料用途。

## 8. 核心状态建议

### 8.0 推广产品销售订单（0.21）

零元：`待审核 → 已开卡 / 审核不通过`；收费：`待付款 → 付款待确认 → 待审核 → 已开卡 / 审核不通过`。凭证退回回到待付款并保留记录；整单取消经过`取消待审核 → 已取消`；记名剩余权益停止由资源方申请`停止待审核`、平台确认后`已停止`，已领取不变。退款、制作/寄送是附属状态，不冒充采购付款或开卡状态。旧导入/开卡状态仅用于历史查询，见REQ-028。

以下状态用于本轮需求讨论，最终状态机在交互和技术设计阶段确认。

### 8.1 客户档案

客户档案是平台级自然人身份，不设置唯一来源资源方。Excel 导入创建时可以为 `未注册/未绑定`，客户完成安全身份验证后进入 `已注册/已绑定`；不记名卡激活必须由已注册/已绑定客户发起。绑定本身不改变 Excel 已分配权益数量，卡激活则按单卡规则新增一笔可使用权益。

### 8.2 客户资源关系

一个客户档案可以同时拥有多条客户资源关系，每条关系只属于一个资源方，并记录关系来自 Excel 名单导入、不记名卡激活或未来其他受控投放方式。关系之间彼此隔离；停用某一资源关系不得删除客户档案、其他资源关系或其他来源权益。

### 8.3 客户权益

每项权益只能有一个明确来源资源方和一种投放模式，并追溯到 Excel 明细或不记名卡；权益记录分配数量、待领取数量、可用数量、预约占用数量和已核销数量，保持数量守恒。相同客户和相同方案的不同来源权益不合并。

Excel 来源权益状态主线为 `待领取 → 可使用 → 预约占用 → 部分使用/已用完`；不记名卡来源权益在卡激活成功时直接从单卡产生 `可使用` 权益，后续状态与 Excel 来源一致。权益可按有效期进入 `已过期`、`已失效`，未领取 Excel 权益也可能因批次回滚进入 `已回滚`，或因停止批次剩余权益进入 `已停止`。Excel 领取只改变状态和数量归类，不新增权益；卡激活按卡片快照新增权益；每次预约和核销使用推广产品中固定的单次核销数量。

### 8.4 预约

状态只使用 `待确认`、`成功`、`完成`、`取消`。

- 客户提交：进入待确认并占用权益；
- 门诊填写不晚于权益到期日的最终预约时间并确认：待确认进入成功，不计费；
- 客户发起改期：预约保持成功且原时间继续有效，改期请求进入待门诊确认；门诊同意后更新最终时间，拒绝或超时则原时间不变；
- 门诊发起改期：操作人确认已与客户协商一致后直接更新最终时间，预约保持成功；
- 关联权益成功核销：成功进入完成；
- 客户主动取消、门诊无法接诊、待确认超时以及后续确认的逾期未核销规则：进入取消并记录不同取消原因；
- 普通错误核销撤销恢复成功；系统自动完成后的补核销撤销仍为系统完成，不建门诊待办，客户申请恢复权益见REQ-037。

不设置已到店、已拒绝或独立爽约状态。任何状态变更均由服务端规则校验，不允许前端任意跳转。

#### 8.4.1 改期请求

客户发起的改期请求使用 `待门诊确认 → 已同意/已拒绝/已超时`，它是预约附属流程而不是预约业务状态。待确认期间原预约时间仍然有效；门诊发起且已确认协商一致的改期直接形成 `已生效` 改期记录。

#### 8.4.2 过期预约待办

过期预约待办与预约主状态独立，任务状态为待处理、待补核销、异常搁置、已关闭。24小时生成，72小时无反馈且无未决改期/冲突时自动完成预约并关闭原待办；权益仍占用、未核销不收费。客户后续报已到诊建立新的补核销待办，原待办历史保留；客户报未到诊按REQ-030释放一次。

### 8.5 门诊

`草稿 → 待审核 → 审核通过 → 服务中`；审核失败进入 `审核不通过`，运营处置可进入 `已下线`、`已暂停` 或 `已终止/退出`。渠道归属变更必须经过下线状态。

### 8.6 错误核销撤销

MVP 不设置客户申请和门诊审核状态。原核销门诊的授权员工执行撤销后，系统保留原核销记录并新增一条不可重复执行的撤销记录，普通撤销恢复成功预约并恢复原占用；特殊补核销撤销按REQ-037恢复系统完成、客户可用余额不增加且不建门诊待办；已结算不得撤销；未结算撤销的账单有效交易移除并留痕。

### 8.7 合作方月度结算单

有可归集交易且本方合计0元时直接生成`无需付款`结算单：保留明细和Excel，不进入对账确认/付款/收款确认，不提醒或逾期，已入单防重复。以下状态链仅适用于正金额单（REQ-042）。

合作方收益单：`待对账确认 → 待付款 → 待确认收款 → 已完成`；确认前异议进入`有异议`，平台回复后重新待对账确认。付款后反馈为单据附属记录，不退回待付款；仅收款方确认实际到账后完成。只为客户资源方和门诊渠道方生成结算单；不生成平台自身收款单。旧`已结账`保留历史状态，不冒充已付款。已确认版本冻结，后续更正通过调整处理；详见REQ-025。

### 8.8 获客服务费

- 预约只占用权益，费用及分配在核销时锁定；核销前不计费。
- 成功核销形成 `已生效未结清` 获客费；账单全部收款经线下审核确认或在线结果核验后进入 `已结清`。
- 结清前错误核销撤销进入 `已撤销`；已完成结算后禁止撤销核销，不新增退款或自动负向调整；未完成结算时撤销移除有效账单交易（REQ-037）。
- 同一预约只能有一条有效主费用链，重复核销/通知/审核不重复计费或结清。

### 8.9 门诊账单与付款记录

- 账单主状态：`待付款 / 付款待确认 / 有异议 / 已逾期 / 已结清`。状态Tab只按账单主状态过滤；付款审核和在线尝试分别展示，不把所有组合扩成账单状态。
- 未结清且过截止日优先显示“已逾期”，即使存在待审核凭证/支付查询中也不能掩盖；未逾期有异议显示“有异议”，否则待审核/待确认时显示“付款待确认”，其余显示“待付款”。全额可信收款完成后已结清，保留原异议及处理历史。
- 线下凭证：`草稿 → 待审核 → 已通过 / 已退回`；退回重提产生新提交记录，不覆盖旧审核。
- 在线支付尝试：`待支付 → 支付成功 / 已关闭 / 支付失败`；超时或结果未知标记“结果待核实”，先查单，不冒充失败或成功。
- 全额确认前不部分冲销；不足额线下到账只增加确认收款、减少剩余应付。真实重复/超额资金独立保存为收款异常，不第二次结清或自动转余额。
- 账单、付款凭证和支付订单各有独立标识，支付结果不能改写核销事实，核销凭证也不能充当付款凭证。

### 8.10 合同

各类合同统一使用 `草稿 → 待审核 → 已审核待生效 → 已生效 → 已到期`；资料问题进入 `审核不通过`，提前解除进入 `已终止`。续签或变更创建新版本，旧版本保留并记录被替代关系，不直接覆盖。

### 8.11 开卡订单、不记名卡批次与单卡

- 销售/开卡订单主线统一按8.0；旧“先审核定价→待收款→已收款待开卡”仅为历史状态，不用于新订单。制作、寄送及退款独立于订单审核主状态；
- 已付款订单取消后记录 `待线下退款 → 已登记退款`，退款状态不代表系统直接执行资金退款；
- 卡批次主线为 `待生成 → 制作中 → 已寄送 → 可发放 → 部分激活/全部激活 → 已关闭`；
- 单卡主线为 `可激活 → 已激活 → 已核销`；未激活卡没有时间过期状态，但可进入 `已作废`，已激活后不得回到可激活，其权益可在激活后 180 天或开卡设置天数届满时过期；
- 争议单卡及其关联权益可由平台进入 `已冻结`，人工核查后回到冻结前状态或受控终止；冻结不得改变原持有人，也不得自动转让；
- 单卡权益支持多数量时，已激活卡在部分核销后保持已激活并记录权益余额，全部用完后进入已核销；单卡状态不得代替客户权益数量账本。

## 10. 非功能要求

### 10.1 可用性与一致性

- Excel 同批次处理、客户匹配/创建、待领取权益分配、不记名卡批次生成和单卡激活、账号绑定、权益领取、预约提交和核销必须具备幂等性；
- 权益领取与 Excel 批次回滚/停止、单卡激活与作废/冻结、预约权益占用与核销、核销与费用记账、线下审核/在线通知与账单结清等关键写操作应保证事务一致性；
- 外部通知失败不得破坏核心业务状态；
- 所有时间使用统一时区和可审计时间戳。

### 10.2 性能与容量

- 批量导入应异步处理并提供进度，不能因单条错误导致全部结果不可见；
- 试点不设机构数、门诊数、客户总数或采购总量的业务配额；不代表无限单文件/单请求或无限并发。单次技术处理量、异步分块、排队、限流及压测目标在详细设计中确定，超限可分批继续，不减少采购或权益总量；原型演示阈值不作为正式业务上限。

### 10.3 易用性与兼容性

- 后台默认中文，信息密度高、待办突出、错误提示可操作；
- 客户端小程序优先保证注册绑定、待领取提示、权益领取、搜索、预约和出示固定二维码短流程；门诊端小程序优先保证预约处理、扫码核销和错误核销撤销短流程；两端均应适配常见手机屏幕；
- 关键状态不能只通过颜色表达。

### 10.4 可审计与可恢复

- 关键数据保留创建人、更新时间、状态历史和来源；
- 批量导入和外部调用支持重试、去重和问题定位；
- 备份、恢复、留存期限和恢复目标在部署设计阶段明确。

## 11. 当前不纳入已确认范围

- 完整口腔病历、处方、影像和治疗计划管理；
- 在线诊疗或医疗诊断建议；
- 微信/支付宝自动代扣、支付宝在线支付、门诊预付余额、平台资金钱包及自动支付分账；门诊账单微信扫码支付已纳入REQ-016；
- 发票信息维护、开票申请、开票记录、税收分类编码、税率和税务接口等全部发票相关能力；
- 客户资源方通过小程序为单个指定客户在线购买并赠送权益；
- 客户资源方与门诊之间的资金结算、补贴和佣金；
- 门诊自己的 CRM、库存、排班和完整 HIS 功能；
- 跨机构共享客户名单或使用客户数据进行无关营销；
- 复杂会员积分、商城和社交裂变；
- 自动对接保险、银行或门诊第三方系统，除非后续明确授权和接口范围。

这些能力不是永久排除；进入范围前需新增需求并完成数据、权限、合规和成本评审。

## 12. 已确认业务规则

### 12.1 已确认的核心规则

1. 客户资源方包括保险公司、银行、经纪代理公司三种固定机构类型，当前不支持配置机构类型。
2. 平台客户以规范化手机号作为唯一主匹配字段，并使用姓名作一致性保护；手机号命中但姓名不一致时作为异常明细，不匹配、不新建同手机号客户。
3. 资源方通常提供客户编号，但不要求批次编号或明细流水号。同批次系统重试保持幂等，不同上传批次暂不区分追加与重复。
4. 导入创建待领取权益。客户登录或注册绑定后主动领取；批次全部权益均未领取时可以整批回滚，任一权益已领取时整批不得回滚。
5. 客户可以在小程序修改允许的个人资料，但不能修改手机号；手机号与姓名冲突不进入平台审核或客户验证更新流程。
6. 不记名卡和 Excel 权益默认有效期均为 180 天，平台在开卡申请或 Excel 批次审核时可以修改；不记名卡从客户激活成功时间起算，Excel 权益从客户领取成功时间起算，不记名卡不设置激活截止日期。
7. 门诊或渠道公司上线、下线优惠后直接生效，不需要平台审核，也不设置门诊配额、每日限额或提前下线限制。
8. 客户提交意向预约时间，由门诊人工确认；系统向门诊预约联系手机号发送短信，并在后台工作台突出待确认预约。
9. 门诊渠道公司不能代门诊确认预约或核销。
10. 客户出示已领取或通过不记名卡激活权益的固定二维码，门诊使用独立门诊端小程序扫码并在线核销；MVP 不使用动态二维码。

### 12.2 已确认的 P1 规则

11. 预约必须关联一项可使用权益，该权益可以来自 Excel 领取或不记名卡激活。客户提交意向时间，门诊沟通后确定不晚于权益到期日的最终日期和时间；预约只使用待确认、成功、完成、取消四种状态。客户可主动取消或在协商后改期，门诊无法接诊时可以取消；核销后预约完成。
12. 优惠下线、门诊暂停、合同到期和门诊退出均不影响已入账权益及状态变化前已有预约履约，只阻止新的预约；门诊确实无法履约时逐条以“无法接诊”原因取消并退回权益。
13. MVP 不建设客户错误核销申诉和门诊审核流程；原核销门诊的授权员工可以在门诊端小程序直接撤销错误核销，系统保留原核销和撤销记录；普通/特殊补核销撤销及已付款退款按REQ-037分别处理。
14. 客户资源方可以查看并导出本方通过 Excel 或不记名卡激活建立关系的客户全部平台允许字段。其他有权业务参与方的一般页面和导出使用脱敏手机号，但当前预约所属门诊的授权员工可以在预约详情查看完整预约手机号。
15. 系统以核销后正式生效的获客服务费为收益基数；合作方每月只归集门诊已结清的历史未入单交易，生成月度收益单及逐笔明细，支持Excel下载；资源方/渠道确认各自对账单，平台登记线下实际付款及全部凭证，合作方分别确认实际到账后完成，平台不另建自身收益结算单；不接入自动资金划转。
16. 所有短信使用系统预配置模板，只有平台管理员可以修改、启停模板配置。
17. 门诊资质至少包括营业执照和医疗机构执业许可证，由平台方审核，完整资料审核时限暂定为 2 个工作日。
18. 当前客户资源方上传模块不要求提交授权证明，不建设专项隐私告知确认和可配置数据保留期限功能，基础安全和平台通用隐私能力仍保留。
19. 一个门诊同一时间只能归属一个渠道公司。归属变更必须先下线，由平台方变更后再上线；变更前已核销业绩保留原渠道；变更后才核销的预约业绩归变更后的渠道，不以预约建立时间分配（REQ-042）。
20. 当前系统不管理“新客”概念，不建立新客标记和统计。
21. 平台/资源方客户权益指标与趋势已按REQ-029开放；其他角色分析、通用统计及经营报表延期，月度结算对账单仍为业务单据。
22. 权益来源展示名由平台按客户资源方分别配置，可以显示实际保险公司品牌而非投放权益的经纪代理公司；资源方只能从本机构列表中选择，不能任意新增或查看其他资源方列表，实际来源机构仍在后台审计链保存。
23. 客户端和门诊端使用两个独立微信小程序，共享服务端但保持入口、登录态、界面和权限分离；同一手机号可以分别具有客户和门诊员工身份，员工身份必须由门诊预先开通。
24. 当前不支持客户手机号修改或换绑，不设计真实换号处置流程。

### 12.3 门诊周期结算规则（0.18替代原授信规则）

25. 取消全部门诊授信、额度调整、额度冻结和风险余额拦截，不要求预付款。
26. 客户提交预约只占用权益；门诊确认保存数量、不锁费，核销时锁定费用与分配并产生应收。
27. 核销时计费及形成三方收益；默认单次1份、1次获客费，按方案独立配置。
28. 核销前取消不计费，权益是否释放按REQ-030；撤销错误核销未结清时冲销费用，已完成结算禁止撤销；未完成结算可撤销并移除账单有效交易（REQ-037）。
29. 不再因欠款金额或预计预约金额达到某个上限阻止搜索/新预约。逾期不自动下线、付款不自动恢复平台人工下线，由平台人工操作，见REQ-037。
30. 周结周一出上周账、出账后3天付款；月结每月1日出上月账、出账后5天付款。均按自然日、出账次日起算（REQ-037）。
31. 支持付款凭证上传后平台管理员审核确认，或微信扫码支付经服务端核实结果后自动记收款；全额到账才整体结清。渠道只查看催收、不担保；发票延期。

### 12.4 已确认的合同与权益投放规则

32. 门诊服务结算改为平台/渠道公司/门诊三方合同；渠道组织签订及续签，平台审核。主体、期限、周结/月结、联系人和完整附件必填；同一时点仅一个有效版本。
33. 结算周期以已审核生效的三方合同为准；续签/变更保留旧版本及历史费用快照。
34. 推广产品销售分不记名实体卡和记名非实体卡；后者支持Excel批量客户及后台单客户。前者激活后绑定，后者审核后待领取。
35. 不记名卡激活前不绑定客户，首次成功扫码激活后归属于当前登录客户且不能再次激活或转让；激活产生的权益必须保留来源资源方、卡批次和单卡记录。
36. 资源方小程序单客购买赠送延期；后台单客户采购纳入REQ-028，仍须平台审核，不能直接发放权益。
37. 资源方填写推广产品、来源、数量和采购价（默认0元），提交统一销售订单；零元直接审核，非零平台确认全额采购款后审核，通过才开卡。实体卡不上传Excel，自动登记唯一号段，平台线下制作寄送。
38. 一个持证经营地址视为一家门诊；同一经营主体可以拥有多个门诊，MVP 的三方合同和账单按门诊分别管理。
39. 每家门诊的待确认预约超时时限可独立配置，默认 24 小时；超时自动取消并释放权益。
40. Excel 错误批次已有领取记录时不能回滚，但可停止该批次尚未领取的剩余权益；已领取部分保留并进入异常处置。
41. 不记名卡执行“未激活可作废、已激活不转让”的最小规则；发生争议时只有平台可以冻结单卡和关联权益并人工裁决。

### 12.5 已确认的改期与逾期处理规则

42. 客户和门诊都可以发起改期。客户发起后必须等待门诊确认，确认前原预约时间继续有效；门诊发起改期时必须确认已经与客户协商一致，确认后直接生效。
43. 所有改期后的预约时间均不得晚于权益到期日，并保留原时间、新时间、发起方、确认方、协商确认、操作时间和处理结果；客户改期请求默认 24 小时未处理则超时，原预约时间不变。
44. 0.23调整：取消2小时提醒；24小时生成过期预约待办，72小时无反馈且无未决改期/冲突时自动完成（不是核销完成），不释放权益、不计费；规则见REQ-030。
45. 客户反馈已到诊、存在未处理改期请求或双方反馈冲突时，不得在 72 小时节点自动释放权益，只保留异常事实并停止自动处置；冲突解决机制及平台异常处理人的权限、期限和专项审计要求暂不实现，待真实案例出现后再评审。
46. 履约提醒、改期请求和异常待办均为预约附属流程，不增加“到店”“改期待确认”或“履约待确认”等预约业务状态；预约主状态仍只有待确认、成功、完成、取消。

### 12.6 已确认的合同、订单与运营规则

47. 合同分为平台—资源方、平台—渠道、平台—渠道—门诊三方合同；资源方和渠道自身的平台合同与方案各自合并为只读页面，门诊合同纳入门诊管理。
48. 取消调额申请及授信冻结；门诊运营暂停权限保留。渠道负责业务员管理本方门诊签约/续签、优惠上下线和催收，须有后台账号并绑定手机号。
49. 门诊合同到期前 30 天，在门诊后台和渠道公司具体负责业务员后台提示；到期后停止新预约，存量预约继续履约。
50. 账单付款期内每天最多向门诊开通联系人和渠道具体负责业务员各发送一次提醒短信，逾期首日再发送一次逾期短信；短信费用、失败重试、服务商对接和模板报备均由平台承担。
51. 渠道公司可以查看门诊账单和欠款并负责催收，但不承担担保责任；发票问题和详细角色权限矩阵暂不讨论，后续专项确定。
52. 资源方可以申请取消开卡订单；订单批次全部卡片均未激活时可整单取消，任一卡已激活则不能取消，MVP 不支持部分取消。退款在线下完成，平台在系统登记退款事实。

### REQ-030 过期预约待办与客户确认恢复权益（0.23）

**目标与范围**：防止未及时核销被误判为爽约或自动释放，同时让客户取回确实未使用的权益。涉及门诊后台、门诊小程序、客户小程序、预约查询及统计/费用口径；不增加平台争议裁决流程、不按系统完成收费、不恢复授信。

| 事件 | 预约主状态/说明 | 权益 | 待办与费用 |
| --- | --- | --- | --- |
| 最终确认时间后24小时仍未处理 | 成功 | 保持占用 | 门诊“过期预约待办”及通知；无费用 |
| 门诊报患者未到 | 取消 / 门诊反馈患者未到 | 保持占用 | 关闭原待办，客户首页提醒；无费用 |

| 客户提交未到诊申请且校验通过 | 取消 / 客户申请未到诊 | 释放原预约占用数量一次 | 关闭客户提醒及相关待办；无费用 |

**业务规则**：

1. 时间按Asia/Shanghai最后一次已确认的预约日期与时分计算；24小时/72小时为连续小时，不是自然日。待确认预约超时取消仍用原门诊级时限且释放权益，不适用本条成功预约的72小时处理。
2. 客户改期待确认时原时间仍有效，但阻止72小时自动处理；门诊确认新时间后按新时间重新计算，旧待办以“已改期”关闭并保留历史。改期双方原审批、协商一致、权益到期限制不变；完成/取消状态不直接改期。
3. 门诊可以从过期预约待办补核销、协商后改期或报“患者未到”。报未到须二次确认“取消预约但不释放权益，客户需自行申请恢复”；任何到诊反馈、冲突或待确认改期存在时不得直接按未到取消，保留事实待核实。
4. 门诊报未到和72小时自动完成后，客户首页显示关联预约、门诊、预约时间、产品外部名称、权益占用数量及处理入口。读过消息不等于处理；客户不操作，提醒及占用持续保留，不自动扣权益或收费。
5. 自动完成详情同时显示主状态“完成”和“预约时间已过72小时，系统自动处理，尚未核销”；不能只用绿色“完成”暗示治疗已完成。门诊报未到显示“已取消，权益仍占用”。
6. 客户按钮为“未到诊，申请恢复权益”“已到诊，完成治疗”，需二次确认。未到申请是本人事实声明，在未核销、原占用存在、无冲突/到诊记录/未决改期时自动通过，不增加门诊审核步骤；已过期的权益只解除占用，不延长有效期，不显示可重新预约。
7. 客户确认已到诊后，新建唯一待补核销任务、提醒门诊；不重开已关闭的原72小时待办。若门诊已报未到则记录双方冲突并异常搁置，不自动认定任一方正确。重复反馈不重复建任务。反馈冲突的标准裁决仍延期。
8. 补核销只能由原预约所属门诊的授权员工，针对原客户、原权益、原占用数量，在门诊小程序扫码核对并确认服务已完成后执行；本次核销时锁定费用/分配；已自动完成但未核销的预约可补核销，已报未到取消的预约不能直接补核销。产品/合同失效不能抹去存量履约承诺；权益有效期按REQ-037检查有效预约日期，不按操作日期拒绝存量补核销。
9. 恢复权益与补核销服务端事务互斥，按预约版本复核并幂等；已恢复不得继续补核销，已核销不得通过未到申请恢复。重复定时任务/通知不得重复建待办、释放、扣减或记费。普通撤销错误核销走独立原流程，不能借未到申请冲销收费。
10. 系统自动完成不产生核销记录、获客费、门诊账单交易或合作方结算分配；客户报已到诊同样不直接计费。有效核销数/核销率仅以真实有效核销为准。REQ-029累计预约仍按待确认+成功+完成统计，可包含系统自动完成；明细必须标注完成来源，避免解释为到诊率。
11. 保存预约/权益/门诊/客户关联、最终时间、完成来源、实际核销状态、反馈来源/时间、任务编号/轮次/关闭原因、权益恢复记录、数量及前后状态。不回写旧“核销完成”为“系统完成”，历史无法证明的数据只读保留，基础审计必需。
12. 通知：24小时提醒门诊；门诊报未到或72小时自动完成触发客户首页待处理消息；客户恢复结果及已到诊待补核销通知原门诊。短信使用平台配置模板，发送失败重试且不回滚业务。原型只模拟本角色通知，不跨端发送。

### REQ-032 门诊资料维护、展示图片和地址定位（0.25）

**目标与范围**：渠道在其管理的门诊详情、门诊在自身后台“门诊资料”中维护同一组业务字段。平台可查看和审核资质；不能借资料编辑修改归属、合同、产品费率、服务状态或审核结果。当前完善后台原型与客户展示预览；未来小程序正式接入共享数据、定位排序和地图，当前不自动获取患者位置。

- 保留门诊名称、经营主体、持证经营地址、营业时间、预约待确认时限（仅只读）等原基本字段。新增独立单张小程序展示图片、门诊业务联系人及电话；原预约联系手机号统一显示为“前台预约手机号”，不是客户预约手机号。业务联系人不等于渠道负责业务员，也不等于合同财务联系人。
- 前台预约手机号必填，按11位大陆手机号校验；门诊业务联系人和联系人电话必填，独立于前台预约手机号，不自动推断或代填。业务电话支持大陆手机或带区号固定电话。旧资料缺失显示待补充，提交资料审核及上线前必须补齐；资料草稿可保留不完整状态，存量缺失不追溯取消预约。
- 展示图可上传、替换、移除及放大预览，只有一张；无图使用中性占位。原型仅PNG/JPG、512KB并校验实际可解码；推荐16:9，预览按同一比例裁切，不强制变形。正式上传需另做内容安全、存储及访问控制，不能只验证后缀；拒绝不合法新图时保留旧图。资质附件不能自动充当客户展示图。
- 前台电话用于客户联系及预约通知；业务联系人和电话仅平台、所属渠道及本门诊可见，不进入客户小程序卡片、地图、公开接口或公开导出。变更前台电话只更新通知目标，不自动修改员工账号、绑定手机号、合同收款人或历史通知记录。
- 地址填写完整省市区、道路门牌、楼层铺位（本轮原型沿用单个详细地址输入，正式服务端做结构化校验）。通过地图服务的地址解析取得候选经纬度；操作员在地图上核对门诊/入口，必要时选点修正后确认。地址解析不保证门店级精度，模糊结果、行政区中心、多候选或失败不能自动确认，可修正地址后重试。
- 保存独立longitude/latitude、coordinateSystem（项目统一GCJ-02）、解析地址快照、服务来源、匹配精度/置信信息（服务实际返回时保存）、定位状态、确认人/时间和变更版本。接口映射明确lng/lat字段，禁止混淆经纬顺序或直接混用WGS84/BD09。校验数值有限、经度[-180,180]、纬度[-90,90]，中国业务还需行政区/POI核对；仅数值合法不代表位置准确。
- 修改地址立即撤销旧位置确认并清空当前可用坐标，保留历史，不允许旧地址解析结果覆盖新地址。正式异步解析须带地址版本校验；解析失败不丢掉表单其他字段，不以0,0或统一默认点冒充门诊位置。
- 已审核门诊的所有资料修改均执行REQ-033：新版本审核通过前不覆盖当前生效资料；退回保留原信息。图片、联系方式、地址、坐标和附件都不能绕过审核，既有预约和合同快照不随资料变更改写。
- 定位状态独立于机构资质及服务状态。允许保存尚未定位的资料草稿；无有效、已核对坐标时不能参加未来“距离最近”排序或显示精确地图点位，但不因此取消已有预约或产生费用。未来距离排序仍先过滤客户权益适用性、门诊产品上线、合同及服务状态；直线距离与驾车距离分别标注，不能混用。客户拒绝位置授权时允许按城市/区域/地址搜索，不强制授权。
- 原型仅对明确标注的虚构演示地址提供固定候选，任意真实地址返回未接入提示；候选、坐标调整及确认均标注模拟。提供小程序卡片预览（图片、名称、地址、前台电话），不包含业务联系人，不伪称已同步两个独立小程序。

**验收**：渠道仅其门诊可维护，门诊仅本门诊；单张图合法上传/替换/失败保留/移除；联系人独立、手机号校验；已保存刷新保留；地址改变使定位失效、失败重试/数值异常/未确认阻断；所有已审核资料变更均重审且退回保留原版（REQ-033）；公开投影不含业务联系人；不同角色仍独立，真实地图服务和小程序定位能力未接入须明确。


#### REQ-032补充：渠道新增/编辑的图片和地图选点（0.25.1）

- 门诊渠道在“录入签约门诊”和“维护门诊资料”均可上传、替换、移除同一张客户小程序展示图片，权限限所属门诊；门诊自身使用同一能力。没有独立的渠道专用图片或平台代传前置步骤，正式系统两方维护同一门诊资料，保存仍受版本及作用域校验。
- 新增及编辑表单都直接提供“门诊位置核对”区，与经营地址相邻；不要求先创建门诊再寻找定位入口。输入完整地址后在地图中查看候选点、道路、周边地标和门诊入口，支持地图点击选点、拖动标记微调、缩放，再确认位置。经纬度由选点自动回填，仅以辅助只读信息展示，不以填写数值替代地图核对。
- 地址为空或解析失败时不能生成默认点位；位置未确认可保存资料草稿但不作为有效定位。重新解析、移动点位、修改地址均撤销旧确认；只有当前地址及当前点位经用户主动核对后才能确认，表单保存才持久化。取消表单不更改门诊定位和图片。
- 当前离线原型用明确标注“虚构示意地图”的道路、地标及候选点演示交互，仅支持三条演示地址；不冒充实际地形、真实POI或地理编码结果，不用于验证真实地址。正式接入必须替换成真实地图/地址检索并保留同一流程，不以示意图验收真实位置准确性。

**补充验收**：渠道新增和编辑均能图片上传/替换/删除及地图确认；门诊自身保持同样交互；点选/拖动/缩放可用、数值只读、移动后须重确认、地址变化后旧点位失效、取消不保存；桌面及窄屏地图和保存按钮可操作。真实地图仍未接入须常驻提示。


### REQ-033 门诊资料版本审核与时限权限（0.26）

**目标/范围**：渠道和门诊修改已审核门诊资料时，旧信息持续有效，新信息经平台审核才替换；取消两方编辑预约待确认时限的能力。

- 待确认时限仍门诊级，默认24小时，只由平台维护；渠道/门诊仅查看，新增时也不能设置。接口拒绝越权字段，不以隐藏控件作为权限控制。平台时限调整独立于资料审核，不修改待审申请中的历史信息。
- 已通过审核的门诊，名称、主体、地址、定位、营业时间、接待/业务联系人、前台手机号、展示图和资质附件等资料变更全部提交平台审核，无“普通字段免审”例外。门诊本身可直接提交变更，不必让渠道代提交。渠道负责业务员变更也按资料申请审核，机构归属/合同/费用仍不可从此流程改动。
- 保存分“当前生效资料”和“资料变更申请”。申请记录完整新资料快照、原生效快照、基准版本、提交人/机构/角色/时间、审核状态/意见/时间。主门诊记录保留原生效资料与资质/服务状态，申请待审核不等于门诊重新入驻或停业。小程序展示、预约通知与定位使用生效版，待审新地址不得与旧坐标混用。
- 同门诊同时只允许一份待审变更；未变更不能重复提交，待审核时双方不能覆盖或重复新建申请。申请一经提交即冻结。退回必须填写原因，可基于退回内容修改后重新提交，形成新申请并保留旧记录。
- 平台审核页同时展示生效版、待审版、字段差异、两版图片和全部资质附件，支持从独立待处理任务页直接处理。审核通过按基准版本检查后一次性替换允许的资料字段；审核不通过仅更新申请状态和原因，不更改原资料、定位、图片、时限、合同或服务状态。重复/过期审核阻断，版本冲突需重新核对提交，不能覆盖较新的信息。
- 尚未首次审核通过的门诊继续原草稿/首次审核流程；首次待审核时也不能静默改写送审资料。旧原型已被覆盖的历史资料不能推断为“已审核快照”，不伪造恢复；正式迁移需可靠审核记录确认。
- 本轮为独立角色浏览器原型；平台独立预置一条明确标注的变更样例，不伪装成跨角色提交自动同步。正式服务端需要机构范围鉴权、版本事务、附件冻结和审计；真实通知、小程序及地图未接入。

**验收**：两方不可编辑或提交时限；已审核门诊任意字段/图片/位置/附件变化进入待审申请，提交/退回不改变生效资料；平台通过后整版生效；退回可修改重提且历史保留；待审重复提交、首次待审修改、越权审核、重复审核和版本冲突被阻止；任务页可审、两版材料可看、状态Tab可用；原合同/预约/账单及上线状态不被申请改写。


### REQ-034 机构管理员、业务员与数据范围（0.27）

- 客户资源方、门诊渠道公司机构账号仅区分管理员和业务员；管理员可看本机构所有数据，业务员仅本人关联业务。暂不提供菜单/按钮权限配置，但既有平台/机构职责边界及账号管理安全规则不取消，业务员不能创建账号或给自己升为管理员。
- 平台新增机构同时创建首个管理员账号，填写姓名、登录手机号；原型不设置真实密码或发送邀请。该账号标记为平台创建且角色锁定，机构管理员不得改变其管理员身份。机构管理员可以另外创建管理员或业务员；角色和手机号校验、重复账号检查及操作留痕必须保留。
- 机构管理员可设置其他账号的管理员/业务员身份，不能通过自改身份或停用最后管理员导致机构失管；平台初始管理员的角色保护不依赖姓名。原型初始账号映射仅针对明确演示编号，真实旧账号必须由平台核对，不通过猜测自动标记。
- 数据过滤同时作用于列表、详情、搜索、Tab计数、导出、工作台、待办、统计和业务写入。渠道业务员以门诊负责业务员ID关联门诊及相关业务；无法唯一匹配的旧负责人不得自动开放。资源方归属口径已确认：推广产品销售订单负责人，默认创建人，关联卡/权益/预约/核销；不能将同一客户其他业务员/来源的权益一起开放。
- 机构公共合作合同与推广产品供本机构账号查看，机构客户/交易/账单并非公共数据。混合多业务员的整张结算单不能因为其中一笔相关就暴露整单；整张机构结算单的确认、异议及收款确认由机构管理员负责，业务员仅查看/导出本人明细、不能处理整单。负责人交接功能按REQ-038延期，不能用部分金额代替整单确认。
- 本轮原型身份切换仅用于同机构评审，不是实际认证。正式登录必须由服务端返回机构/账号/身份/范围；浏览器不得自行声明管理员。服务器按业务关联ID鉴权，前端过滤不是生产隔离。

### REQ-035 门诊上下线入口与对象操作日志（0.27）

- 平台门诊管理列表每行提供独立“上线/下线”操作，使用弹窗显示门诊、当前状态、影响和必填原因；移除详情资料页“暂停接入新预约”动作。上线仍需资质、有效合同、无业务冻结/退出等阻断条件；逾期不作为自动阻断，平台核对后人工决定，下线仅停止新预约，不抹除存量履约及已生效资料。
- 门诊详情新增“操作记录”分区，按该门诊编号汇集录入、资料提交/审核、合同、推广产品、上下线等事件，不展示其他门诊日志。门诊自身资料维护事件也记录。审核意见、上下线原因和状态变化应可追踪。
- 门诊账单、平台与资源方/渠道的收益结算单及采购订单详情提供操作日志：出单（有记录时）、确认/异议、付款凭证、审核/退回、支付查单、结清、平台付款及收款确认等。日志有操作时间、操作人/机构/身份、动作、原因、结果/状态和记录编号。系统事件标为系统，不伪造人为操作；历史缺字段显示未记录。
- 日志只读，按当前对象及账号数据范围显示；不记录密码、Token、图片内容或完整联系方式。新动作记录真实事件时间及前后状态/变更字段名，不把完整表单快照写进通用日志。生效资料/附件快照仍在专门的版本业务数据中。
- 仅原型角色内事件即时留痕，不伪造后台跨机构汇集。正式事件与业务写入须事务一致、不可篡改、幂等，并记录真实认证主体；本轮无真实短信、资金操作或生产审计服务。

**验收**：新增机构必建角色锁定管理员；本机构管理员可创建两类账号且不能改锁定账号角色；业务员范围隔离及无法确定归属时关闭访问；平台列表上下线弹窗必填原因、阻断上线条件保留；门诊和各类账单/采购订单详情操作记录包含新动作及历史缺失说明、无敏感载荷。数据归属未确认部分不得宣称生产就绪。


### REQ-036 门诊移动身份、账单付款与客户预约短流程（0.28）

**目标/范围**：门诊小程序区分管理员与员工，缩短客户预约及到诊出码路径；同步门诊后台创建账号文案，不改变资源方/渠道的“管理员 / 业务员”、机构数据范围或结算计费规则。

- 门诊后台账号角色统一显示“管理员 / 员工”。门诊小程序仅预开通、有效且已绑定账号可登录，普通手机号不能自注册为员工。旧无身份依据的移动登录须重新选择演示身份，不自动提升为管理员。
- 管理员可处理本门诊预约履约、查看合同/账单并付款；员工只处理本门诊预约相关工作。本轮将核销、补核销、错误核销撤销及过期预约待办保留为预约履约工作，不授予账单、合同、付款凭证或支付记录权限。预约逐笔核销费用/结算状态仍按REQ-025展示，不等同整单权限。
- 合同、账单、付款入口及相关提醒只对管理员展示；直接路由/提交同样检查身份。合同由渠道签订/续签、平台审核的职责不变，门诊小程序管理员查看合同并联系渠道，不新增自行签约或审核权限。
- 管理员账单详情同时提供“微信支付”和“上传付款凭证”。移动支付采用同机发起支付交互，不要求扫码自身屏幕。金额绑定当前账单及版本，不任意修改；未支付、取消、失败、未知均不能结清，仅服务端可信结果可记账。原型仅显式模拟结果，非真实支付。
- 凭证提交需实际附件、付款金额、时间、付款方及交易参考号；提交后待平台审核，不允许门诊自行确认到账。退回保留记录并允许重提；在线未决与线下待审互斥，保留日志。沿用REQ-016全额结清及部分到账不冲销规则，不新增自动退款。
- 客户“我的权益”卡片内直接展示来源、剩余份数、有效期和产品使用规则快照（单次份数、适用门诊及使用条件）；可使用卡片主按钮为“预约门诊”，携带所选权益直达适用门诊列表，不再提供“查看权益”。待领取卡片直接领取；占用/过期/冻结/用完显示原因，不允许新预约。旧权益详情链接保留兼容，不改变领取/激活事实。
- 客户预约详情直接展示该预约关联权益的固定核销二维码，无须再点“出示权益凭证”。码不含手机号等敏感信息、不得随打开页面生成新的权益或扣减份数，沿用固定凭证身份。
- 仅有效已确认、占用足额且未核销的预约展示可用码；系统超时完成且符合补核销条件的预约同样可展示。待确认、取消（含未释放）、已核销、预约日期超期/权益冻结、未领取、已恢复或存在改期/冲突阻断时展示不可核销原因，不显示可用码。展示不是核销授权，扫码仍须服务端实时验证全部条件；原型仍为不可真实核销的视觉示意。

**数据/安全边界**：账号身份、凭证/支付尝试/审核与日志分别记录；合同及账单服务端按本门诊管理员鉴权，前端隐藏只是辅助。本轮各组本地虚构数据独立，不接真实微信、共享账号或跨端付款审核；不新增细粒度角色矩阵。

**验收**：管理员/员工登录及刷新、员工入口/深链接拦截；后台角色选项与旧缓存兼容但资源方/渠道不改名；管理员两种付款路径、附件错误、取消/未知/失败/待审和重复操作不误结清；权益卡规则/直达且保留所选权益，失效卡无法预约；打开预约详情即有适用固定码，重复打开不改码或权益，取消/核销/恢复后隐藏，系统完成仍沿用补核销校验；375/390/430px可读、原预约及核销/撤销回归通过。


### REQ-037 核销、结算及登录规则确认（0.29）

**状态/范围**：本轮用户确认的业务规则。替代所有早期冲突描述；原型、旧测试和ADR中的旧演示事实不代表已实现本条。用户本轮后续澄清优先：自然日次日起算；已结算不得撤销核销、未结算撤销移除有效交易。交接功能延期至上线后考虑（REQ-038），本期仅保留负责关系与历史事实分离的架构约束。

1. **锁费时点**：获客费及其分配在核销时锁定，预约提交/确认不锁费。核销前向门诊展示本次实际获客费，平台按权限查看分配依据；不向门诊暴露其他合作方费率；同一事务校验规则版本、保存费用及分配快照、核销和记账，网络重试不按新价格再次记账。单次权益消耗份数及客户获赠承诺不因分配变更而更改。已核销金额和撤销退款依据仍取原交易快照，不能拿撤销当日价格倒算。存量合作合同已到期、无可解析分配版本时不得默认套用其他机构或零费用，应明确待核实，保留存量履约承诺。
2. **有效期判断**：预约日期及改期后日期均不得晚于权益到期日；核销/补核销按最后已确认、生效的预约日期判断是否在权益有效期内，不以实际扫码日替代。例：权益9月30日到期、预约9月30日、10月2日补核销，不因10月2日超过到期日而拒绝；预约10月1日则不能提交、确认或核销。未决改期不替换原日期，也不放开既有改期冲突限制。只有这条日期判断变化，身份、关联门诊、已完成服务、占用足额、冻结、已取消/恢复、幂等检查均保留；禁止核销端任意补填预约日。
3. **期限**：各合作方月结为出账后5个自然日、周结为出账后3个自然日，出账当天不计入，从次日起算；不跳过周末或节假日。项目截止时刻采用最后一天23:59:59（Asia/Shanghai）。例：9月1日出月单，9月6日截止；9月7日出周单，9月10日截止。这里确认的是付款期限；客户资源方及渠道方仍按月出账，不增加周结模式；对账确认与收款确认不新增独立超时自动处理。
4. **周期变更**：合同结算周期变更立即生效，不追溯已出账单；不绕过原渠道提交/平台审核的合同变更权限。“立即”指有权审批使变更生效后。新周期接管全部尚未出账交易，在下一新周期出账日归集，原已出账交易排除；本轮不擅自增加“修改合同即即时出账”行为。服务费所属周期和当时合同版本留痕。
5. **撤销核销与账单（以后续确认覆盖先前退款想法）**：账单已完成结算（全额确认到账/已结清）的交易不得再撤销核销；不再实现“已结算后撤销并退款”。没有出账或账单未完成结算时可按原权限撤销，费用不再应收，从当前账单有效交易列表及合计移除该笔，其他交易不变。这里的删除是解除有效账单明细关联并记录账单新版本，不物理删除原核销、原账单版本或撤销审计。交易不得以后又被归集为有效费用/收益。账单状态、未决支付和金额变更须同事务复核；若线上结果未知或有待审实际收款，先核实结果再判断是否已结算，不能用旧页面绕过已结算限制。重复撤销不重复扣减合计。采购销售订单既有取消/线下退款规则不受此条影响。撤销后整单无有效交易时应停止收款、保留取消原因和历史，不制造一笔真实收款；具体空单展示可在交互设计中统一。
6. **异常款范围**：重复/超额付款暂不闭环，不建设自动退回或余额账户；真实款项仍保留，不吞流水、不重复结清、不标成已退款。保留基础防重和账实异常提示，不将“暂不闭环”解释为取消支付幂等。
7. **账单与人员权限**：机构管理员处理本机构整张结算单，业务员仅查看本人权限内逐笔明细及其合计；不泄露其他业务员的客户或交易，不显示过滤后合计为整单金额。查看、导出、Tab计数和汇总采用同一范围，业务员没有整单确认/异议/收款确认权限。
8. **登录**：四类Web后台统一手机号+短信验证码，预先开通账号及有效机构身份才可登录；客户和门诊小程序统一微信手机号授权，门诊员工须预开通。没有验证码或手机号授权不能以浏览器选择身份代替认证。技术方案应提供有效期、单次使用、防刷及登录失败控制，不新增用户未要求的小程序短信登录备用入口。
9. **逾期和上下线**：门诊支付逾期只显示状态、欠款和提醒，不自动下线或停止新预约；平台通过已有上下线弹窗人工处理并记录原因。付款后也不自动撤销人工下线，须平台上线；资质、合同、产品权限等其他限制继续执行。不得以“逾期状态”在搜索/提交/上线校验中暗中实现自动阻断。
10. **撤销系统完成后的补核销**：仅在相关账单未完成结算时可执行；恢复到“完成 / 系统自动完成（补核销已撤销）”，不是成功；不直接恢复客户可用权益、不新增或重开门诊待办。客户小程序新增持久待处理消息，可提交恢复权益申请。恢复请求关联本次撤销记录，避免因历史“已到诊”反馈而永久阻止本轮申请；按撤销事实、未再次有效核销、当前权限及数量复核，最多恢复一次。不直接放开自动再次补核销，避免绕过已关闭的处理流程。
11. **特殊撤销的权益数量（已确认）**：撤销后从本次有效已使用数量转为“待恢复”，不进入可预约余额，也不继续作为有效核销消耗；待恢复份数与其他可用/占用/已使用份数分别计数、总量守恒，不重复统计。客户收到“补核销已撤销，您有权益待恢复”的消息，使用“申请恢复权益”操作后自动校验并释放一次。该入口不是要求客户谎报未到诊，不沿用已到诊历史事实对普通未到申请的阻断。未申请持续待恢复，不生成门诊待办。申请不延长有效期，已到期的权益解除待恢复后仍过期，不能新预约。

**验收范围**：预约后调价、核销时锁定/重复请求；到期日预约次日补核销允许及超期预约/未生效改期拒绝；自然日次日起算的截止日测试；周期修改不重出已出账；已结算撤销拒绝/未结算移除且合计正确/历史留存及并发已付款保护；逾期不自动阻断/结清不自动上线；管理员整单与业务员明细隔离；两种登录身份；特殊撤销保留系统完成、无门诊待办、客户恢复申请一次及已过期不延期。

**本轮澄清已收敛**：自然日次日起算、已结算禁止撤销核销/未结算移除有效交易、特殊撤销先待恢复后申请释放均已确认。未出账交易按新的账期出账已确认；已出账交易不重排。平台收益为获客费扣除两方收益后的余额，所有金额四舍五入至分；先分别计算两方金额并舍入，平台取剩余分值以保持三方合计等于获客费。禁止超额分配，不使用浮点误差改变半分舍入结果。

### REQ-038 业务员交接延期与数据设计约束（已确认）

**范围决定**：业务员交接功能暂不处理，系统上线后再按实际情况讨论。移出本期MVP、原型及功能开发范围，不作为本期上线的待确认阻塞项。既有账号停用、机构管理员全机构权限、业务员本人范围和管理员处理整单等已确认功能不受影响。

**本期必须遵循的设计约束**：

- 当前负责人关系与历史创建人、实际操作人、来源机构、历史渠道及收益快照分开表达，不能将可变负责人同时用作不可变交易事实。
- 保持资源方销售订单、渠道门诊等业务对象的稳定ID；客户权益、预约、核销和账单通过稳定业务关联追溯，不通过复制业务员姓名/手机号作为关联键。
- 服务端数据范围判断从负责关系及已有机构/业务关联解析，避免在每一条下游业务记录中重复保存并依赖可变负责人。为查询效率存在的缓存或投影不是唯一权威数据源。
- 未来交接应能通过调整必要的负责关系实现，不要求逐条迁移客户、卡片、权益、预约、核销及账单；历史归因和已锁定费用不因负责人变更被改写。这里只约束数据耦合，不承诺任何规模下零写入或零迁移。
- 本期不提前建设交接页面、交接单、审批、批处理队列、接收确认、交接回滚或历史可见范围配置；也不预建复杂账号继承体系或完整交接数据表。具体方案上线后再定。

**本期验收方式**：详细设计评审检查数据字典、关联关系、权限查询依据和历史字段语义，能够说明未来如何更换负责关系而无需全量改写下游交易。仅保留最小解耦约束，不要求现在完成交接功能或交接专项测试。

此前详细建议保存在[ADR-0015](decisions/0015-responsibility-handover-proposal.md)作为历史参考，不是本期开发清单。


### REQ-039 门诊预约确认提醒小窗（0.29.2，已确认）

**目标/用户/范围**：降低门诊前台切换浏览器Tab或使用其他软件时漏掉预约确认的风险。仅门诊Web后台、当前门诊具有预约处理权限的管理员/员工使用；平台、渠道、资源方及两个小程序不增加此浮窗。采用真实Document Picture-in-Picture常驻窗口，默认紧凑，人工展开/收起。不改变预约确认时限、权限、权益和计费规则；原短信及工作台待办继续保留。

**交付状态**：本轮只落地需求、设计和验收标准，不修改原型代码。0.29.1已实现的是手动开启400×520大窗试用，不代表以下登录联动、紧凑态和展开/收起已经完成。TASK-067记录文档，TASK-068/069跟踪后续原型与正式接入；ADR-0018补充ADR-0017。

#### 开启、关闭与登录

1. 门诊登录页“登录时开启预约提醒”默认勾选，前台可取消；本机偏好只影响此提醒，不改变认证或机构权限。此偏好不是必须主动勾选的法律授权或业务确认。首次使用或没有偏好时默认开启；普通关闭浮窗不永久关闭下次登录的默认设置。
2. “登录默认打开”指用户主动点击登录按钮时一并请求创建小窗，不要求登录成功后再点第二个开启按钮。为满足浏览器用户手势限制，点击时先请求窗口，只显示“正在登录”；服务端认证成功且确认当前门诊和权限后，才查询和展示预约。登录失败、无门诊权限或取消登录时关闭预开窗口；窗口申请失败不影响正常登录。
3. 不承诺等待异步登录返回后仍能开启；登录页与后台须保持同一来源文档生命周期。若登录必须整页跳转、自动恢复会话、刷新页面或浏览器拒绝开启，则进入后台后显示“预约提醒未开启”，由用户点击工作台“开启预约提醒”。不能用脚本模拟点击绕过限制。
4. 工作台始终保留“开启预约提醒”按钮，并显示未开启/已开启/不可用的实际状态。已开启时再次点击只唤起同一窗口，不重建、不丢失当前展开状态。同一来源页最多一个提醒窗口。
5. 用户点击浏览器关闭按钮后停止此窗口提醒，新预约不会自动重新打开；后台待办和短信继续。退出登录、账号失效或切换身份/门诊时及时清除旧数据并关闭窗口；关闭或刷新来源页同样结束浮窗。重新开启须主动操作，不显示上一账号/门诊的缓存预约。

#### 紧凑态、提醒态与展开态

| 场景 | 展示与行为 |
| --- | --- |
| 已登录、首次查询中 | “正在获取预约”，不显示零或“暂无”冒充查询结果 |
| 查询成功，待确认数为0 | 尽可能小的常驻窗口，显示“暂无待处理预约”和“展开” |
| 登录/重新开启时已有待确认预约 | 警告色及“有 M 条预约待确认”，不把存量全部称为刚到达的新预约 |
| 本次监听收到新预约且仍待确认 | 小窗自动切为Arco警告色，显示“有 N 条新预约”；另标“共 M 条待确认”（有存量时尤须明确），不自动放大、抢焦点或重开窗口 |
| 点击“展开” | 在同一窗口中请求调整为较大的预约处理窗口，展示待确认总数、列表与“去处理”入口，保留“收起”；不是另开第二个窗口 |
| 处理部分或全部预约 | 数量按真实状态更新；无待确认时显示“暂无待处理预约”，已展开窗口不自动收缩或关闭 |
| 点击“收起” | 同一窗口恢复紧凑态，继续监听；可在仍有待办时收起，提醒数量和警告状态保留 |
| 连接中断/数据刷新失败 | “连接中断，预约信息可能未更新”，显示最后更新时间及重试入口；旧数字注明非最新，不显示“暂无”或伪装连接正常 |

- “默认小窗尽可能小”按浏览器允许的尺寸、系统缩放及文字可读性实现；项目初始设计参考320×120 CSS像素，展开参考400×520，均非硬性承诺或Arco官方尺寸。正文不小于14px、辅助不小于12px，按钮保持可点，不能为细条效果裁掉提醒或系统标题栏。具体最小尺寸在目标前台电脑验证后调整。
- 展开和收起都由真实点击触发尺寸请求；浏览器不支持缩放或拒绝时保留可读内容，提示可手动调整尺寸，不假装已改变窗口大小。窗口位置由浏览器/用户控制，不能承诺固定右下角。
- 新预约到达只改变内容、颜色和数字，最多一次短动效，不持续闪烁；同时提供文字提示并尊重减少动效设置。本轮不增加声音、操作系统桌面通知、浏览器扩展或桌面客户端。
- 展开列表使用Arco“待确认（M）”状态Tab，展示本门诊预约编号、意向日期/时间及“去处理”。“去处理”回原后台独立待处理任务页并定位该预约、直接打开原业务表单，沿用确认最终时间/无法接诊等已有规则；不跳普通列表要求再次查找，不在浮窗创建第二套确认流程。
- 已在其他页面、门诊小程序或其他授权员工处处理的预约，以服务端最新状态移出待确认列表；点击旧记录先复核，已处理则提示结果，不重复确认。进入详情、展开、收起、关闭或看过提醒都不等于处理预约，不停止待确认超时计时。

- 试点规模不设业务数量配额，不限定机构/门诊/客户总数或总开卡量。文件大小、单次解析量、后台任务分块及并发限流属于资源保护，由详细设计和服务器验证确定，必须有进度、可恢复失败及继续分批的路径，不宣称无限吞吐。
